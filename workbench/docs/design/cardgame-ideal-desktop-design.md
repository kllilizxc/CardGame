# 理想卡牌开发桌面：AI 全驱管线与三张内容地图

> 2026-09-26：下一阶段规划见 [游戏创作桌面整体方案](cardgame-creation-studio-plan.md)。用户最新要求为“自动制作到试玩，确认后加入游戏源码”，且允许改造游戏本体；下文的默认正式采用、限定便笺改造范围等旧决策不再作为下一阶段约束。此处保留历史设计，新方案尚未实施。

2026-09-19。本文是"理想设计"，在现有卡牌工作台（七便笺、14 连接，见 `cardgame-workbench-design.md` 与 `plugins/cardgame-content/README.md`）之上推演，不受现有实现约束。覆盖卡牌战斗、剧情与爬塔地图三类内容。

## 出发点：用户只剩四个动作

用户几乎不亲自做结构性工作，但会直接微调内容——一句话达不到理想效果是常态。整个桌面围绕这个事实设计，用户的全部职责是：

1. **说想法** —— 对助手说一句话，或往 Todo 扔一条草稿。不需要分类、不需要写清楚，AI 负责分诊、补全、派发。
2. **试玩** —— 打开试玩便笺玩游戏，玩完说感受。感受自动变成 Todo。
3. **微调** —— 在知识库、资源库、卡牌库里直接改（入口现有便笺已提供，不新增）。手动改动是正式输入：必须自动同步到试玩与合入提案，且不被后续 AI 生成覆盖。同步机制见下文"微调同步"。
4. **否决（可选）** —— 看到不满意的资源候选或方案时点反对。默认不审批，管线全自动流转。

其余一切——写作、绘图、编曲、改数值、修断链、整理资料、起服务、跑测试——都是 AI 的工作。衡量设计好坏的唯一标准：**用户一周不打开管线便笺，游戏依然在变多、变好；用户随手改的每个字，都活着到达试玩。**

## 便笺全景：八张，分两组

便笺数量保持小规模（延续"一种便笺是一种专注工具，内部管大量条目"的原则）。画布上分两个分组：

**左侧分组「内容」（权威数据，AI 天天读写，用户只来微调）**

| 便笺 | 管什么 | 关键形态 |
| --- | --- | --- |
| 知识库 | 剧情、人物、世界观、规则、内容使用关系 | 自由 Markdown + 链接，已有模板 |
| 卡牌库 | 数千张卡的定义、数值、标签、版本 | 表格/卡面网格，已有模板 |
| 爬塔图 | 幕/层/节点/路径、难度曲线、事件分配 | **新增便笺**，图形化地图 |
| 资源库 | 图片、动画、音效及其全部历史版本 | 按媒介分视图，已有模板 |

**右侧分组「管线」（工作流，用户主要看这里）**

| 便笺 | 管什么 | 用户接触频率 |
| --- | --- | --- |
| Todo | 想法、反馈、缺陷、优先级的唯一入口 | 高：唯一书写入口 |
| 执行台 | 所有 AI 长任务的实际执行与结果 | 中：看进度 |
| AI 生产 | 素材制作请求、候选、采用事实 | 低：只来否决 |
| 试玩 | 运行游戏候选版本 | 高：主要活动场所 |

不新增"总控台"便笺。健康状态（断链、缺图、数值异常）由定时巡检直接写成 Todo，不带长期未读红点进入用户视野——巡检见下文"自动化机制"。

## 便笺内部：从操作台到观察窗

**本轮范围**：知识库、Todo、执行台、试玩四张便笺内部**保持现状**，沿用现有模板不重构。内部重设计只落在**卡牌库、资源库、AI 生产**三张既有便笺，以及新建的**爬塔图**上。

现有便笺的内部结构是为"人来操作"设计的：搜索、筛选、表单、批量操作。本设计里主要操作者是 AI，用户的主诉是"审阅 AI 干了什么，偶尔纠正"。因此参与重构的便笺按同一骨架组织：

### 统一骨架：三层 + 对话

每张便笺的 expanded 视图固定为三区：

1. **变化流（顶部）**：这个领域最近发生了什么——谁改的（AI/人工/巡检）、改了什么、影响面多大。用户不操作系统，系统必须主动向用户汇报。默认只显示最近几条，可翻历史。这是用户打开便笺时最先看到的东西，回答"我不在的时候发生了什么"。
2. **内容区（中部）**：该领域的本职视图（卡面、地图、网格……），以读为主。
3. **干预区（选中即出现）**：用户选中任何内容（一张卡、一个节点、一个资源）后，出现该对象的详情与微调入口。

对话不新增输入组件：**复用便笺自身的 AI 会话**（便笺本就有独立对话能力）。要做的只有两件事：

- 视图里给一个常驻入口（按钮/快捷键），打开的是**本便笺自己的对话**，不是另一个聊天面板；
- **选中对象作为上下文自动带入**——用户选中一张卡说"这张降一费"，AI 知道是哪张；选中一个地图节点说"这层太难"，AI 知道是哪层。

**对话是微调的第一入口，亲手编辑是第二入口**；很多"微调"用户更愿意说而不是改。只有当便笺会话确实承载不了的场景（目前没有），才考虑额外输入组件。

Compact 模式的职责随之重定义：不再是迷你操作台，而是**该领域的实时摘要**——最近在变什么、有没有需要用户看一眼的事。没有就不打扰。点击 compact 卡片的任何条目，展开并定位到该内容。

### 来源标记贯穿所有视图

每个内容对象（卡牌、资源版本、地图节点）都携带来源：AI 生成 / 人工微调 / 混合。视图里用轻量标记区分（不强视觉，但求可查）。这既是"人工版本不被覆盖"纪律的界面体现，也让用户审阅变化流时能一眼看出哪些该细看——人工改过的被 AI 再动，永远值得标红。

### 各便笺内部设计

**卡牌库**。内容区默认卡面网格（外观审阅是用户最高频的卡牌动作），表格比较视图退为切换。单卡详情 = 卡面 + 数值 + 来源 + 使用位置链接。微调两档：数值直接在详情里改（带版本校验），批量规则走便笺对话（选中一批卡说"3 费以上的攻击卡数值降 10%"，AI 执行并给 diff 预览）。变化流回答：哪些卡被新建/改数值/退役，各自来自哪条 Todo。

**爬塔图**。内容区 = 当前幕的节点地图渲染，可缩放，节点按状态着色（未装配/装配中/已编译/需复核）。点节点 → 干预区显示该节点的引用装配（剧情、遭遇、奖励池）与编译状态。用户几乎不在这里编辑数据——选中节点说"这层太难"，由 AI 调参数并回显 diff。整塔统计（难度曲线、奖励密度）在展开侧栏，主要供用户审阅 AI 的平衡结论。变化流回答：哪层被重新装配、为什么、编译结果如何。

**资源库**。内容区 = 缩略图流，默认按"最近采用"排序——用户来这里的主要场景是审阅 AI 新出的图/音效。每张候选/版本上最显眼的按钮是**否决**（回退上一版 + 自动建返修 Todo），其次才是查看历史与编辑标签。微调（改标签、改名、选版本）保持现有能力。音效维持"同一便笺只播一条"。变化流回答：哪些资源新入库、自动采用了哪版、哪些被否决重修。

**AI 生产**。候选对比视图是核心：同一请求的候选并排，默认显示 AI 的推荐理由。用户动作收敛为两个：点选采用（通常不用，自动采用已生效）、点否决（附一句话原因更好，不附也行）。批次状态、在制进度只读。

**知识库 / Todo / 执行台 / 试玩（保持现状）**。四张便笺内部不动：知识库微调走现有源码编辑入口；反馈与想法走现有对话和 Todo 入口；执行台维持现有任务观察与操作方式；试玩维持现有运行控制。微调的后端同步（见"微调同步"）与便笺内部无关，照常生效。后续若需要，统一骨架可平移过来。

## 爬塔图便笺（核心新增）

爬塔是第三类内容，既不是文档也不是卡牌，需要自己的权威入口：

- **数据即文件**：每幕一个 JSON（节点、边、类型、难度参数），与剧情 Markdown、卡牌定义同级，编译进游戏。便笺只是它的图形界面。
- **视图即地图**：画布式层叠节点图（战斗/精英/休息/商店/事件/首领），AI 直接改 JSON，用户看到的是渲染结果。用户想改，说一句话，不动手拖。
- **节点是装配点不是内容**：每个节点只存引用——事件节点链到知识库某篇剧情，战斗节点链到卡牌库的遭遇定义，奖励节点引用卡池。剧情正文和卡牌数值永远只有一个家。
- **局部视图**：默认只看当前幕当前层；整塔统计（路径长度分布、难度曲线、奖励密度）作为展开视图，供 AI 做平衡时读取。

## 连线设计：三层语义

连线是 AI 之间的协作路线，分三层，规则不同：

### L1 资料参考（只读，无 action）

执行台和生产便笺对四张内容便笺各拉一条参考连线（共 4 条），instruction 写明"先检索再读取、只取必要段落、不把全库装进上下文"。这是 AI 干活时的取料通道。

### L2 交办与回执（成对，显式 invoke）

创作性工作需要判断，保持现有的"显式交办 + 长 instruction + repair 回流"模式：

| 连线 | 方向 | 干什么 |
| --- | --- | --- |
| 交办 | Todo → 执行台 | 用户想法变成执行任务（已有） |
| 结果回写 | 执行台 → Todo | 完成/失败结论回写（已有） |
| 素材草稿 | Todo → 生产 | 含素材需求的 Todo 自动建制作草稿（已有） |
| 生成 | 生产 → 执行台 | 不可变需求快照提交生成（已有） |
| 候选登记/采用 | 生产 → 资源库 | 产物入库与版本采用（已有） |
| 试玩投递/回执 | 执行台 ↔ 试玩 | 可玩候选启动与结果反馈（已有） |
| **铺层** | 爬塔图 → 执行台 | 新增：把一层节点装配成具体内容 |
| **铺层回执** | 执行台 → 爬塔图 | 新增：生成结果与编译错误回写节点 |

"铺层"是爬塔的核心闭环：AI 在爬塔图上规划好一层 → 沿连线交办执行台 → 执行台读知识库（剧情钩子）和卡牌库（敌人与奖励池）→ 生成遭遇与事件内容 → 回执写回节点状态。

### L3 事实同步（watch，机械幂等）

与 L2 不同，纯事实的传播不需要 AI 判断，应该用 `watch: true` 自动投递（这是对现有"全部 watch:false"的主要改变）：

| 连线 | 触发 | 效果 |
| --- | --- | --- |
| 卡牌退役 → 爬塔图 | 卡牌状态变为弃用 | 引用该卡的节点标记"需重新装配"，进 Todo |
| 资源采用 → 内容引用方 | 新版本被采用 | 使用处清单刷新，旧版本标记可归档 |
| 编译错误 → Todo | 内容编译产出错误 | 自动建 Todo，定位到文件与段落 |

原则：**机械事实走 watch 自动同步，创作协作走显式 invoke**。watch 投递必须幂等、带指纹去重，repair 失败回投到来源便笺。

## 微调同步：手动改动进入管线

微调不新增便笺——知识库的源码编辑、资源库的版本与信息编辑、卡牌库的 JSON 编辑（均带版本校验）就是入口，用外部编辑器改原文件同样算数。设计要解决的是三个问题：

**1. 落盘即被看见。** 文件是唯一真相源，内容索引本就支持增量更新；手动保存后索引立即重扫该文件，重算链接与引用。便笺视图不允许缓存冒充当前文件（延续容量设计的既有约束）。

**2. 影响面自动传导到预览与提案。** 一次微调沿引用链传导：改了剧情文件 → 引用它的场景与爬塔节点标记"内容已变" → 编译器重编译受影响场景；改了资源版本 → 使用该资源的卡面、场景、清单刷新；改了卡牌数值 → 引用该卡的遭遇标记待复核。传导终点永远是两个：**试玩**（候选自动重建，重启即见新效果）与**合入提案**（手动改动与 AI 产物进入同一条提案流，提案中标注哪些是人工改动——PR 不丢任何一边，也不把人工改动误记为 AI 产物）。

**3. 人工改动不被覆盖。** 每次手动微调登记为"人工版本"。后续 AI 重新生成同一段剧情、同一资源、同一张卡时，必须以人工版本为基线做 diff：保留人工块，AI 只改其余部分；整体重生成只能作为候选并排对比。静默覆盖人工改动算事故，经 repair 回路升级为高优先级 Todo。

实现注意：文件变更来自内容索引而非便笺状态，因此这条传导不走 connection 的 watch（watch 订阅的是便笺 state/config），而由内容服务的索引事件直接驱动重编译任务，产出再沿既有连线流动。

实施状态（2026-09-19）：剧情域已闭环——`compileStory` 编译器落地（`scene: true` + `## 选项` 约定，输出 StoryState 并幂等登记 content-catalog），每次编译把入口与全部源文档记入 `story_builds` 表；文档保存/移动/外部编辑触发索引更新后，受影响剧情自动重编译。重编译失败保留上一份可用产物，diagnostics 写进 `story_builds` 并由每日巡检汇总成 Todo；入口或源文档被移动/重命名时依赖记录自动跟随（`remapStoryBuildPaths`），storyId 保持稳定。提案的"人工来源标注"依赖来源标记（阶段三），仍未实现。

## 自动化机制（连线之外的发动机）

**1. 轻量内容编译约定**（现有设计留白的"Markdown → 游戏剧情"）。不强制表单，只做两条最小约定：

- 文档 frontmatter 里 `scene: true` 表示这篇可被编译为游戏场景；其余文件永远是纯资料。
- 场景内标题为 `## 选项` 的章节下，链接列表即玩家分支；正文其他位置的链接永远只是作者参考。

编译器作为内容服务的一个命令运行，输出游戏运行时数据；错误精确定位到源文件段落并自动生成 Todo。转换失败不影响资料存在。

**2. 定时巡检**（schedule，不进画布）。每日一次：断链扫描、孤儿资源、卡面缺失、数值离群（费用/伤害分布异常）、剧情死路（选项指向不存在的场景）。结果写成带优先级的 Todo，其中纯机械修复（如重命名后的链接跟随）巡检直接修掉并在 Todo 里留痕。

**3. 自动采用策略**。资源候选通过机检（尺寸、帧数、格式、透明度规范）后自动采用为当前版本，不经用户审批；用户在资源库或试玩中否决时，回退上一版本并建返修 Todo。审批从"每步闸门"降级为"事后否决权"。

**4. 单一反馈漏斗**。任何便笺里产生的任何不满，统一 funnel 到 Todo——不在资源库、试玩、爬塔图各建反馈台账（延续现有约束）。用户在试玩时说一句"这层太难了"，助手负责翻译成爬塔图某层的难度参数调整任务。

## 用户的一天

打开桌面 → 试玩便笺已经在跑最新候选 → 玩十分钟 → 对助手说"第二张地图的商店总是没好卡，还有开头剧情图错了" → 助手拆成两条 Todo，一条走爬塔图重新装配奖励池，一条走生产便笺重出图 → 顺手在知识库把某段对话改了两个字，保存，试玩重启即生效，这次改动自动进了同一条合入提案 → 用户关掉桌面。几小时后巡检、生成、装配、编译自动完成，下次打开试玩就是新版本。

## 分阶段落地

1. **阶段一（现有基础上补齐）**：定时巡检 + 编译错误 → Todo 的 watch 连线；明确自动采用策略；微调传导链（索引事件 → 重编译 → 候选重建 → 提案标注）。便笺内部只做三张：卡牌库、资源库加"变化流"区和"选中对象带入便笺对话"的上下文桥，AI 生产加候选对比与一键否决。知识库、Todo、执行台、试玩模板不动。
2. **阶段二（爬塔）**：定义幕 JSON 结构与编译约定，新建爬塔图便笺模板（含变化流与上下文带入对话），接通"铺层"两条连线。
3. **阶段三（深化自动同步）**：卡牌退役、资源采用两条 watch 连线；人工版本基线与 diff 保留纪律落地到生产与铺层流程；来源标记进入卡牌库、资源库、爬塔图视图；评估把更多机械事实从显式 invoke 迁移到 watch。

## 验收方式

延续容量验收思路，补三条管线验收：

- 给定"新增一层爬塔内容"的 Todo，从交办到可试玩候选的全流程不经过任何人工编辑；统计每一步耗时与人工介入次数，人工介入应为零（否决与微调除外）。
- 在知识库手动改一段剧情文本，不改任何其他东西：试玩候选在限定时间内反映该改动，合入提案包含该改动且标注为人工来源；随后让 AI 重写该场景，人工改动的那一段保持原样。
