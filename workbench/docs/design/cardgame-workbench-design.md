# CardGame 便笺系统设计：文件优先、职责单一、面向大量内容

2026-09-19 修订。目标项目：/home/kllilizxc/Code/CardGame。本版本取代之前的“世界与剧情便笺、试玩与反馈、资源内维护使用关系”的设计。

本轮范围为便笺职责、信息组织、交互与容量设计。AI 制作流程、模型选择及游戏内容编译约定另行确定。

## 确定的约束

- 剧情由知识库内的普通 Markdown 文件管理，自由正文、文件链接、锚点与图片构成主要写作方式。
- 不强制场景表单、节点类型、固定模板或必填元数据；外部编辑器、源码编辑、对话修改都可以操作原文件。
- 知识库管理剧情、人物设定、规则说明和内容使用关系；链接与派生反向链接索引表达关系。
- 试玩只负责运行与体验；反馈、缺陷、想法、修改要求归 Todo。
- 资源库只管理资源本身；使用位置通过一个链接跳到知识库。
- 像素美术、spritesheet 与其他资源全部由 AI 生产，用户不承担绘制、补帧、修图和手工整理海量素材。
- 按数千篇剧情、数千张卡牌、上万项资源、数百条音效设计；便笺数量保持小规模。

## 设计单位

一张便笺是一种专注工具，内部可以管理大量条目。文件、卡牌、资源、版本、制作任务分别有自己的身份，不为每条内容创建独立便笺。

各领域有明确的权威入口。其他便笺通过链接定位过去，并保留来时的查询、选中项和阅读位置。跳转不会强制同步改变全部便笺的工作范围。

## 主便笺职责

| 便笺 | 核心职责 | 展开结构 | 边界 |
| --- | --- | --- | --- |
| 知识库 | Markdown、说明、引用与反向链接 | 目录/收藏 → 搜索结果 → 当前文件；源码/阅读切换 | 叙事、设定、使用关系统一在这里 |
| 卡牌库 | 检索、定义、数值、规则、卡面、版本 | 查询 → 表格/网格 → 单卡详情 | 剧情出处与使用位置链接到知识库 |
| 资源库 | 找、看、选、管理文件与版本 | 保存的筛选 → 列表/网格 → 当前资源 | 不复制剧情、使用关系和反馈系统 |
| AI 资源生产 | 制作请求、输入、候选、实际制作状态、产物 | 批次/请求 → 当前制作 → 候选与产物 | 成品进入资源库；长期需求、缺陷和反馈归 Todo |
| Todo | 想法、需求、反馈、缺陷、优先级、事项状态 | 查询/分组 → 事项列表 → 单条事项 | 通过链接附带上下文，其他便笺不自建反馈台账 |
| 执行台 | 实际执行、运行状态、结果、错误 | 当前工作 → 执行详情 → 产物入口 | Todo 管要做什么，执行台管实际执行 |
| 试玩 | 版本、启动、停止、重启、测试入口、存档 | 必要运行控制 + 尽量大的游戏画面 | 不放反馈表单、剧情编辑、素材说明和任务管理 |

现有功能进展可继续作为独立辅助便笺，不增加一个承包所有领域的制作总览。天气等个人便笺不在本次调整范围。

## 知识库：自由写作与大量文件导航

文件是唯一正文来源。目录按章节、地区或主题组织都可以，跨目录关系通过普通 Markdown 链接完成。例如：

    # 问心阶前

    少女在人群中停下，袖口的青玉铃微微一响。

    ![青云宗山门](../../assets/backgrounds/qingyun-gate.png)

    你可以[扶她一把](./help-girl.md)，也可以[继续排队](./keep-waiting.md)。

    > 人物设定：[持铃少女](../../characters/bell-girl.md)

以上路径为示例。文字和链接的位置不被固定表单限制，图片仍使用普通引用语法。

任意文档链接都应正常导航。哪些链接在游戏里成为分支选项、哪些只是作者参考，属于后续的轻量内容约定；不能把全部链接直接当作玩家选项，也不能为此把所有知识文件套入同一种场景格式。

知识库需要：

1. **目录按需展开**：只加载展开的目录和当前结果，提供面包屑、收藏、最近文件。
2. **文件名与全文搜索**：按目录范围、中文关键词、精确短语和路径查找，结果显示命中片段与位置。
3. **文内导航**：支持相对路径、锚点、同名文件、前进后退，以及目标文件快速预览。
4. **真正显示图片**：正文按需加载预览，点开再取大图；保持原始 Markdown 图片引用。
5. **反向链接**：按需查看谁引用了文件或资源，定位来源文件和段落；从正文派生，避免手工维护另一份关系表。
6. **移动与重命名**：预览受影响的链接，再统一更新；外部编辑造成的断链也能检测和定位。
7. **局部关系图**：只展示当前文件或一章的一两层关联；它是阅读辅助，不限制写作。
8. **可选元数据**：支持 frontmatter，但不要求每篇文件填写；基本索引从标题和路径派生，稳定身份可由内部登记。

普通文件始终能读写。能否转换成可玩内容是另一种状态，转换错误应定位到源文件和段落，不影响资料继续存在。

## 卡牌库：服务数千张卡的检索与比较

默认入口是查询结果。按名称、ID、类别、费用、标签、状态等现有定义筛选；实际字段从游戏数据中选择，不为界面额外强加设定。

表格适合密集比较，卡面网格适合外观检查，两者共享查询与选中项。支持少量卡牌并排比较定义或版本。

卡牌定义文件保留原有来源，便笺提供定位和必要编辑能力。故事背景等解释继续写 Markdown，卡牌详情只提供“在知识库打开”。卡牌创作文本如何生成运行时字段，后续另定。

批量操作明确区分当前页、明确选中集合和全部匹配，预览范围与结果；列表变化不能悄悄扩大已经确认的操作范围。

## 资源库：上万项资源与更多历史版本

一个资源条目代表一种可复用素材。候选版本、不同导出尺寸、原始素材和可用文件归在条目下面。默认只显示每项资源的当前版本，展开再看历史，避免十个候选让主列表膨胀十倍。

资源详情只展示名称、稳定身份、类型、尺寸/时长、帧数、格式、版本、文件位置、收藏与资源自身标签。叙事用途和使用位置通过“在知识库打开”跳转。

媒介采用适合自己的视图：

- 图片与背景：缩略图网格，可切换紧凑列表。
- spritesheet 与动画：列表默认静态封面，选中再播放；支持逐帧、速度和循环。
- 声音：紧凑列表，显示时长，按需加载波形和试听；同一便笺默认只播放一条。
- 技术筛选：类型、格式、尺寸、帧数、时长与版本状态。

命名、基础说明和初始标签由生产结果或 AI 辅助建立，用户可修改；管理万项素材不能依赖逐个手工填写。

“背景”“像素角色”“短音效”等查询可保存。声音增多时，可以钉一张“声音库”便笺，它仍是同一资源库的音频视图，不拥有另一份文件或版本。

同文件去重与相似候选比较是不同能力，相似不自动合并或删除。无索引引用不等于可安全删除；是否使用由知识库及运行内容的明确引用范围判断。

## AI 资源生产、Todo、执行台的边界

Todo 保存“要做什么、为什么、优先级”；生产便笺保存“制作输入、哪一轮候选、产物”；执行台保存“实际执行状态与结果”。

生产界面可以比较候选、选择版本。已形成的修改需求、缺陷和返修意见统一归 Todo，不在资源库、试玩和生产界面各维护一套反馈状态。详细派发方式与生产流程后续设计。

所有资源加工由 AI 或其调用的制作能力完成，用户不成为隐含的补帧、抠图和整理节点。

## 共同交互

- 收起时展示少量最近项、收藏或一个当前工作，不同步全量条目。
- 展开恢复该便笺自己的查询、选中项和阅读位置。
- 保存的是查询或目录入口，结果动态更新，不复制资源或文件。
- 深链接打开文件、锚点、卡牌、资源或试玩版本；名称变化仍需可追溯。
- 历史版本、已完成事项和旧批次默认折叠，按需查询。
- 中文搜索需要用真实中文名称、正文与别名验证；语义搜索补充精确检索。
- 每种主要操作可以只用键盘完成；返回列表后保留位置，便于连续处理大量条目。

## 容量设计：第一版就要具备

以下是设计要求，不代表现有系统已经达到性能目标。

**文件、索引与便笺状态分开。** 正文和二进制保留为文件；可重建的持久索引保存搜索字段、链接和媒体基础信息；便笺状态仅保存配置、查询、选中项和必要工作状态。不能把上万条资源写成一个巨大的共享状态数组。

**检索在后端完成。** 先查询索引取得有限结果，再读正文或媒体。使用稳定排序、分页或游标及前端虚拟列表，不能先把全库传进浏览器再筛选。

**媒体按需加载。** 缩略图与原图分开，封面与完整动画分开，波形与音频解码分开。只渲染可见条目和有限预加载项；已翻过的页与解码缓存有上限。

**增量更新。** 改一个文件只重查受影响的链接和内容；刷新一个资源只更新相应条目。索引尚未同步或检查失败要可识别，缓存不能冒充当前文件。

**关系与 AI 上下文也有边界。** 反向链接分页，关系图只读局部。AI 先检索再读取必要段落和有限关联，不把全部剧情、素材与历史任务装进每次会话。

**后台与界面独立。** 隐藏便笺停止不必要的媒体工作，实际后台生产由执行系统持有。其他便笺打开时不必重载整个项目。

## 未来实现的验收规模

| 内容 | 建议验收数量 |
| --- | ---: |
| 剧情 Markdown | 3,000 篇，含图片、中文名称和跨目录链接 |
| 卡牌 | 3,000 张 |
| 图片、动画等资源 | 20,000 项 |
| 音效与音乐 | 600 条 |
| 资源历史 | 平均每项 5 版，约 100,000 个历史条目 |
| Todo、制作记录 | 各 10,000 条，含大量已完成历史 |

检查初次打开是否读取全库、查询是否只取有限结果、媒体是否按需解码、连续浏览后内存是否持续增长、单文件修改是否造成全列表重建、重命名能否定位受影响链接，以及多个便笺同时工作时是否互相拖慢。响应时间指标在明确目标机器与典型素材大小后制定并实测。

## 当前实现与建设顺序

已有知识库支持按文件读取、相对 Markdown 链接与有限正文缓存。当前 templates/reference-note/view.tsx 的图片渲染器只显示文字占位，真实图片、资源解析与按需加载需要补充。

现有画布和便笺状态能力不能直接视作万级内容管理能力。查询索引、分页、媒体预览、中文检索与大数据验收要落实到知识库、卡牌库、资源库的数据层。

先固定权威来源与职责；优先补知识库的链接、图片、搜索和目录导航，资源库的查询、版本与媒体预览；卡牌库复用相同的浏览原则。保留 Todo、执行台、试玩各自的职责，再设计具体 AI 生产流程。
