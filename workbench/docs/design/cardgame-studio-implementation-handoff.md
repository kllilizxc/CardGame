# Worka 游戏创作工作流：实施交接

2026-09-26。交接给执行 agent；本文件说明接下来如何在已有实现上落地，不要求重新设计或从头重做。

## 1. 任务与阅读顺序

目标：用户通过便笺原生对话提供游戏 idea，AI 处理内容、素材、组装、代码接入与检查，自动形成可试玩的候选；用户体验并明确确认后，才将该候选加入正式游戏源码。最终达到可发布、不会编程的 10 岁使用者也能完成创作的标准。游戏本体允许作必要工程改造。

从现有单卡链路开始实施，先完成下文 M0 + M1，通过后再扩展复杂冒险、长篇剧情和完整游戏。不要再交付一份宏观规划代替实现，也不要先重画整套桌面。

读取顺序：

1. 当前仓库的 AGENTS.md、[CONTRIBUTING.md](../../CONTRIBUTING.md)；改 UI 再读[设计入口](../../design/index.md)及相关规范。修改 CardGame 前读该仓库 AGENTS.md。
2. 本交接文档，尤其第 2 节用户约束和第 6 节首批任务。
3. [总规划](cardgame-creation-studio-plan.md)：功能进展最小扩展、对象分工、候选/采用协议、素材目录和里程碑。
4. [人物与长篇剧情方案](cardgame-narrative-system-plan.md)：进入 M2 时必读。
5. [现有单卡验收记录](../verification/card-workflow-2026-09-26.md)、[内容后端说明](../../plugins/cardgame-content/README.md)、[预览 v2 契约](../preview-adapters.md)。

决策优先级：用户最新指示 → 本文与总规划中的最新收敛约束 → 叙事专项方案 → 其他旧设计及原型。现有代码决定“已经实现什么”，不能用设计文档推断完成状态。[早期卡牌工作流](card-generation-workflow.md)、[旧理想桌面](cardgame-ideal-desktop-design.md)、[原工作台方案](cardgame-workbench-design.md)仅作历史依据；其中逐阶段人工批准、到处增加讨论/交付按钮等已被后续要求覆盖。

## 2. 用户已经确定的边界

| 事项 | 必须遵守 |
| --- | --- |
| 增量实施 | 用户明确说“不用从头做”。复用现有便笺、数据服务、组件、流程、游戏场景；每次改动对应一个实际缺口。 |
| 创作对话 | 只用 DSH 已有消息面板和便笺自带的会话按钮。内容区不加聊天面板、输入框、消息历史、“在 DSH 中讨论”或同义图标/按钮。 |
| 游戏试玩 | 只在现有试玩便笺运行。其他便笺和功能进展不加“试玩这段冒险”“试玩这里”。候选自动登记，保留版本，不抢焦点或强制导航。 |
| 游戏画面 | 游戏保持固定 16:9 比例；不把手机端适配列为本项目验收项。Worka 便笺自身仍按其现有界面规范检查。 |
| 最终采用 | “加入我的游戏”、采用记录、撤销统一在现有功能进展的对应功能项中。其他内容页不放采用按钮，也不追加固定“查看功能进展”底栏。 |
| 功能进展 | 保留现有功能列表、搜索/筛选、展开/折叠、归档、决策记录、PR/CI/部署与 DEV/PRE/MAIN 展示。compact 保留摘要。只按需补候选版本、确认采用与记录。 |
| UI 克制 | 默认展示当前内容和必要轻操作；详细参数、引用、历史按需展开。不要给每种对象/资源创建便笺，不堆叠流程条、状态徽标、说明栏和操作教学。 |
| 现有能力优先 | 适用于所有便笺。新增界面前先核对现有文档、链接、搜索、引用和共享组件能否完成任务；确有缺口时优先扩展通用能力。知识库的章节、人物及主题先用 Markdown 索引页和普通链接组织，不另做专用剧情目录。 |
| 生图选择 | 默认使用 Codex 生图。当前会话能生图不等于 Worka 有自动调用接口；验证受支持交接方式。未经同意不替换成收费服务。 |
| 卡面主题 | 保留已制作的青云山灵狐、青玉/宣纸两主题。插画、定义、布局与动态数值分开，切换主题不改玩法。 |
| 内容完整 | 覆盖卡牌/卡组、世界、人物、剧情/游戏任务、道具、规则、经济、UI/引导，以及声音、背景、立绘、图标、字体、动效、过场和按需的 3D。 |
| 人物与剧情 | 能力、关系、知识和物品真实影响事件、选项与后果；主角需要成长/队伍/装备等状态。按长篇组织，不能用三个对白节点交差。 |
| 实施与发布 | 必要的 Worka 与游戏工程改动可实施；生成内容进入正式项目仍须绑定确切候选的用户确认。日常实现不用反复确认；全量测试、额外付费服务和公开发布不视为已授权。 |

功能进展的具体最小方案：制作状态补入现有摘要、下一步和决策记录，保留用户写过的内容；存在合格候选时才出现确认入口；采用历史和撤销放在该功能项可展开的记录中。采用事实由业务服务提供，PR 合并、CI 成功、部署成功保持各自原有含义。

## 6. 首个实施批次：M0 + M1

### M0：把基线与能力验证做具体

1. 记录两仓库已有相关改动及真实便笺/项目身份，列出本批改动与验收项。保留当前单卡成功路径作为回归基线。
2. 追踪所有正式写入口，包括 updateCard、savePipelineCard、compileStory、adoptVersion、adoptAsset、integrateCard、switchCardTheme、项目默认主题写入和执行台文件工具。确认候选作用域能贯通后端，不能只移动前端按钮。
3. 单独验证 Codex 图像交接：固定请求 → 受支持执行端 → 返回图像及来源 → 登记对应候选 → 继续组装。区分可自动、需人工交接、不可用；旧请求不能回填新要求。未接通时明确结论，不抓取会话或假设隐藏 API。
4. 验证现有 v2 预览契约对游戏的适配方式：确切提交、托管工作区、服务入口、验证与进程恢复；确定候选存档隔离方案。

生图接入若暂时受阻，继续能独立完成的候选隔离、预览和采用服务工作。可复用现有灵狐图验证这些部分，但不能因此宣称“新 idea 自动生图”的完整路径通过。

### M1：完成一张卡的真实循环

| 顺序 | 具体工作 | 验收产物 |
| --- | --- | --- |
| 1. 候选与引用 | 扩展现有 workflow/production，关联 projectId、featureId、创作事项、基线、对象 revision、素材版本和预览候选；便笺 state 只存展示偏好与定位 | 一份可查询、可恢复的真实候选及依赖清单 |
| 2. 隔离读写 | 内容、资源采用、编译和工具写入默认落到该候选范围；索引/监听按范围区分；保留正式项目已有人工修改 | 未确认前，正式内容文件与存档不被创作流程改写 |
| 3. 自动制作 | 复用草稿、素材、模板组装、版本和错误恢复；将“固定草稿版本”与“用户批准”分开，不强迫每张卡逐阶段点批准 | 原生对话到可检查候选；选择素材不能冒记为用户批准 |
| 4. 真实可玩 | 继续用青云山灵狐 CR_001 与已有两主题；固定已有玩法，打通正常获得/进入场景的路径以及实际使用；迁移至 v2 托管预览 | 在试玩便笺中体验确切版本，能观察主题和真实游戏行为 |
| 5. 原生对话上下文 | 发送消息时绑定便笺、项目、对象/选中集合、版本与候选；打开或切换对象不先运行一轮模型 | 用便笺自带按钮调整卡牌/主题，结果回到对应候选；内容区无第二个讨论入口 |
| 6. 最小采用接入 | 在现有功能项上加候选与确认；旧 production/library 正式写入动作改走同一采用校验；记录与撤销归该功能项 | 保留现有功能进展 UI/行为，同时能确认一个确切候选 |
| 7. 恢复与回退 | 持久应用日志、项目级串行、重复确认幂等、外部变更冲突、失败恢复和反向变更 | 可定位的采用回执；中断不留半包；撤销不抹掉用户后续编辑 |

采用确认绑定 `featureId + candidateHash + targetBaseRevision + validationManifest`。试玩的快照固定，新的改动产生新候选；不能将 `HEAD+worktree.<hash>` 一类描述字符串当作可检出的提交。v2 负责工作区、端口和进程，项目适配器只描述启动与业务验证。

独立目录或不同端口不会自动隔离浏览器存档，必须按 project/candidate/profile 明确命名空间。采用时重新检查目标基线和依赖闭包，冲突产生新候选并使旧确认失效。加入本地源码不等于 push、部署或发布。

## 7. 后续实施顺序与完整范围

| 阶段 | 交付重点 | 进入下一阶段前的依据 |
| --- | --- | --- |
| M2a | 雾林冒险：世界、主角/NPC、道具、条件剧情、任务、遭遇、奖励卡及背景/立绘/图标/基础声音/UI | 高低属性、知识/关系/物品门槛、正常与替代路线、奖励幂等、场景切换和存档实际通过 |
| M2b | 500–1,000 条真实对白的一章；跨章人物/事实、稳定 ID、分块阅读/编译与长篇压力 | 真实章节的阅读/修改/游玩验收和容量压力分别出证据 |
| M3 | 新机制、确定性场景、六卡种及各显示位置、主题一致性 | 实际新增机制能触发、检查、采用与回退，旧行为不回归 |
| M4 | 从新游戏 idea 初始化母版、主循环、菜单/教程/设置和内容组合 | 新项目完成独立游玩循环，项目间数据与存档隔离 |
| M5 | 创作桌面可安装交付、游戏独立 Web 包、发布/恢复、目标用户验证 | 干净环境和真实新手测试通过，分别报告工具与游戏的交付能力 |

### 内容归属

卡牌库负责卡牌、卡组、解锁/获得和主题；世界负责区域、据点、秘境、路由、交互、碰撞/寻路与遭遇。知识库通过现有 Markdown 文档、索引页和链接组织人物、剧情、游戏任务、道具、战斗/成长、经济/制作、游戏界面/引导、世界设定八类内容；只有实测通用能力不足时才扩展共享查询或阅读组件。待办仍是创作需求与反馈，不与游戏任务混用。

道具至少覆盖消耗品、装备、钥匙/工具、任务物、材料与货币。交付包括获得、堆叠、持有/装备、使用/消耗、交易/丢弃限制、条件、反馈、存档与图标/声音引用。例如满生命不吞药、装备卸下撤掉修正、工具检查不误消耗银针、满包/合成失败不扣部分材料。

### 素材归属

资源库保留一个入口，生产任务归 AI 资源生产，执行事实归执行台：

| 类别 | 覆盖 |
| --- | --- |
| 人物 | 角色参考、头像、立绘、表情、姿势、服装、探索小人 |
| 场景 | 背景、前后景/遮挡、地块、昼夜/天气、场景物件、小地图 |
| 图标 | 道具、装备、货币、技能、状态、标记与光标 |
| 卡牌 | 插画、卡背、边框、稀有度、布局与主题源件 |
| 声音 | 音乐、环境音、交互/战斗音效、对白/旁白配音；循环、分轨音量和事件/台词绑定 |
| UI/字体 | 组件与全部必要状态、皮肤、布局、中文字体/回退、本地化、标题封面和发布图标 |
| 动效/过场 | 程序动效、粒子、序列帧/图集、镜头、演出时间线、按需视频与字幕 |
| 3D | 模型、UV、材质/纹理、骨骼/蒙皮、动作、灯光/相机与渲染配方 |

玩法定义、用途、媒介格式和制作方法分开；没有实际文件的素材需求不能伪造为 ready asset。资源记录原件、变体、衍生、来源、版本、配方和引用；模型源件与 2D 渲染输出分开。UI 用组件实现排版/行为，图片只承担适合的表现部分，不能整页烘焙。

首版优先 2D、现有/导入声音、代码 UI 和少量程序动效。全配音、复杂动画、视频与 3D 按具体需求启用，各有能力验证；不为补齐目录而默认生成全套。每个创作配方自动检查玩法、画面、声音、界面/操作、存档/兼容、入口与退出/验证六类需求，优先复用，不能让用户逐项提醒遗漏。

### 人物与长篇最低要求

人物定义与每个存档实例分离。能力注册保留 ID、范围、修正来源；主角/NPC 共用基础，主角再加成长、队伍、装备、持有物和选择。关系有方向，秘密/事实与谁知道它分别记录。既有 0–100 属性不能直接替换成原型中的 0–10 示例数值。

事件触发、选项可见、选项可选、执行效果分开。条件、消耗、奖励与事实变更一致提交；已有 StoryState 求值、visibleWhen/enabledWhen 继续复用。长篇采用章节→场景→对白片段/选项、稳定 ID、局部上下文、增量编译与存档迁移；全文巨型图不是默认编辑界面。

原型与专项方案的章节、信任数值、人设是不同层次的示例，不能混作两份正式剧情。M2/N1 以叙事专项第 5 节为条件验收基准，固定一份可执行样例；工具是否消耗按道具定义，银针与耗材分开。剧情内容定稿进入候选再确认。

长篇第一档目标见专项第 9 节：至少 30 万有效中文字符、20 章/20,000 条对白旁白、200 人物、50 任务、3,000 选项、5,000 已声明状态键。以上未实测，不是当前能力。压力数据与真实文学章节分别验收，报告关键路线覆盖，不能宣称穷举全部剧情。

## 8. 验证与交付要求

使用 Bun，按改动选择直接相关的最小测试集合，不运行无文件范围的全量 `bun test`。以下是定位清单，不是要求一次全部执行：

| 改动 | 优先查看/运行 |
| --- | --- |
| 卡牌制作与存储 | `tests/cardgame-card-pipeline.test.ts`、`cardgame-workflow.test.ts`、`cardgame-production-integration.test.ts` |
| 内容、资源与库 | `tests/cardgame-content.test.ts`、`cardgame-library.test.ts`、`cardgame-media.test.ts`、`media-capabilities.test.ts` |
| 显式关联 | `tests/cardgame-connections.test.ts`；只在涉及安装/调度时检查对应 schedule 测试 |
| 预览 | `tests/preview/workspaces.test.ts`、`tests/candidate-preview-view.test.ts`，再按涉及模块选择 protocol/state/ports 等测试 |
| 功能进展 | `tests/feature-tracker-provider.test.ts`、`tests/core/official-feature-tracker.test.ts` 中受影响案例，并补候选/采用契约回归 |
| 剧情 | Worka `tests/cardgame-compile.test.ts`；CardGame 的 `StoryState.test.ts`、`storyFlow.test.ts`、`storyFlowViewModel.test.ts` 及受影响存档测试 |
| 游戏卡面 | CardGame `src/game/objects/cardFaceAppearance.test.ts` 及实际受影响预览组件测试 |
| 容量 | 仅进入相应阶段时在隔离数据目录使用 scale 测试/压力样例，不能往真实游戏填充模拟全书 |

Worka 实现改动按 CONTRIBUTING 执行 `bun run typecheck`、相应构建/打包和受影响便笺检查；宿主、协议或生命周期变化需用可丢弃 DSH profile 验证。CardGame 使用已存在的 `bun run dev-nolog` / `bun run build-nolog` 和所选 colocated 测试；构建通过不代表类型与行为全通过。

UI 先核对现有同类组件与数据契约；使用共享 NoteIcon/HeroUI、响应式规范。实际读取便笺尺寸后验收 compact/expanded、深浅主题、窄屏、长文本和错误状态。纯布局不加镜像实现测试；数据、并发、采用和生命周期补有意义的回归。

每个完成批次交付：实现的文件/行为、真实入口与版本、执行过的命令和结果、浏览器验收、未验证范围、剩余阻碍及下一步。验证记录放 `docs/verification/`，区分历史证据与本次重跑。更新既有功能记录，避免创建重复事项；纯规划和讨论不登记成已实施功能。

没有完成的能力保留真实状态。生图交接缺失、候选不完整、音频/模型没有文件、检查过期时，不能用绿色状态或假预览掩盖。已确认要求无需反复询问；遇到会改变费用、权限或重大产品取舍的真实缺口时，先完成不依赖它的工作，再给用户一个具体问题。
