# Worka 游戏创作桌面：从一句想法到可发布游戏

2026-09-26 · 下一阶段产品与工程规划。状态：**方案，尚未实施**。

本方案依据正在运行的卡牌游戏桌面、CardGame 当前源码、已完成的单卡工作流，以及用户最新要求制定。游戏本体允许改造；本轮交付规划与交互草案，不修改运行中的制作流程和游戏规则。

最新要求优先：**自动处理到可试玩版本，用户确认后才加入游戏源码。** 本文取代旧理想方案中的“默认自动采用正式素材”“只改部分便笺内部”“仅以爬塔覆盖地图”等约束。保留原生对话、文件优先、领域身份稳定、小规模便笺管理大量内容的原则。

**演进方式：在现有系统上增量完善，不从头重做。** 先复用已有便笺、数据、组件和工作流，再补实际缺少的能力。功能进展保留现有界面结构与工程跟踪；原型中的单功能选择器、交付总览布局和独立确认页不作为整体改版要求。其他内容与素材规划继续保留，按实际缺口分批接入。

**对话硬约束：所有创作、编辑和反馈对话只复用 DSH 现有消息面板，以及便笺自带的会话按钮。** Worka 不新增聊天面板、输入框、消息气泡、会话历史或独立模型调用链；内容区域也不再增加“在 DSH 中讨论”、同义按钮或替代图标。原生入口负责读取选中对象上下文，结果回到内容区域。游戏中 NPC 与玩家的剧情对话属于游戏玩法，不在此创作 UI 约束范围内。

**交付硬约束：统一在现有「功能进展」中确认加入游戏、查看采用记录和撤销。** 卡牌库、世界、知识库、资源生产和试玩便笺各自承担本职，不放置“加入我的游戏”，也不统一追加“查看功能进展”底栏。DSH 中明确的采用指令也必须关联到同一个功能项并调用同一交付能力。

**界面收敛：试玩集中在现有试玩便笺；每项操作只在其归属位置提供。** 内容便笺和功能进展不增加“试玩这段冒险”“试玩这里”等快捷入口，不把删掉的按钮换成图标或藏进另一菜单。内容区域默认只展示对象及必要的本地编辑操作。工作流生成候选后自动登记到试玩便笺，不强制跳转或抢焦点；原生对话入口自动携带选择，不重复绘制讨论区。重复的流程条、全局采用徽标和操作教学文案一并收敛，必要错误和待决事项仍使用现有反馈方式。

**叙事能力修订：人物与剧情按可制作长篇剧情游戏规划。** 主角/NPC 的能力、关系、知识、经历与任务状态必须真实影响事件和选择；十几万字、一章几百至上千条对白需要分层组织、局部编辑、跨章记忆和容量验收。默认操作仍简单。具体模型、雾林条件示例及验收见[人物、任务与长篇剧情方案](cardgame-narrative-system-plan.md)，本文件原有简短冒险和交互草案不代表能力上限，也不证明这些能力已经实现。

**完整性修订：原型必须覆盖完整游戏所需的内容与素材，不只覆盖卡牌。** 本轮验收包括道具的获得/使用/消耗/条件、卡牌之外的图片与声音、UI/字体/动效/过场、按需采用的 3D 源件，以及它们与人物、场景、剧情和功能项的关系。延续上面的对话、试玩、采用入口约束；不因补齐类型而给每种素材新建便笺，不把规格草案标为已生成资源。

## 1. 产品目标与首版边界

目标体验：用户说出一个想法，AI 理解已有游戏，自动制作、接入、检查和启动候选；用户在便笺原生对话里修改，实际试玩，最后确认加入游戏。失败由系统定位并在限额内修复，成功后保留可回退的版本。

用户只需要理解五个动作：**说想法、看结果、说怎么改、试玩、加入我的游戏**。任务拆分、ID、文件路径、素材回填、构建、工作树和测试属于后台工作。

第一款母版以现有“修仙世界探索 + 剧情选择 + 秘境搜打撤 + 卡牌战斗”为基础。新游戏 idea 可以改变世界设定、主角、关卡、卡组、玩法目标和风格，系统从母版组合出一段完整可玩的游戏。其他类型的游戏可以通过新增母版扩展；首版不承诺任意类型的一句话游戏都能稳定完成。

保留 React + Phaser 和现有可用场景，按接口逐步改造。允许修改引擎内的玩法实现，但每一处结构调整都应服务一个具体的创作或试玩闭环。

“能发布”分两项验收：

- **创作桌面能交付给别人**：新环境可安装、能力可检查、失败可恢复、无需作者代为操作。
- **做出的游戏能交付给玩家**：独立构建可运行，不依赖本机 Worka、开发服务器或创作时的模型会话；包含菜单、教程、存档、内容入口和完整的小型游玩循环。

## 2. 现状判断：基础可复用，端到端仍有断点

| 现有事实 | 对新方案的意义 | 下一步 |
| --- | --- | --- |
| 七张主便笺：知识库、卡牌库、资源库、AI 资源生产、待办、执行台、试玩；14 条显式关联 | 已有职责和身份，无需重新造一组业务系统 | 保留对象 ID、状态、会话及关联，以新的创作视图组织 |
| 桌面另有功能进展，使用 official-feature-tracker 的稳定功能 ID，当前主要展示 PR、CI 与部署事实 | 作为统一交付入口已有基础，尚未具备游戏采用能力 | 扩展同一功能项的候选、验收与采用引用，保留原交付跟踪 |
| 实际桌面同时展示资料、生产、执行、试玩等工具，当前视角缩放后文字较小 | 初学者需要自行理解工具和交接关系 | 默认聚焦当前想法、当前内容与试玩，完整画布保留 |

| `card-pipeline.ts` 有持久阶段、CAS、过期回执保护和单卡恢复 | 是可扩展的业务基础 | 复用记录与资源服务，新增候选范围及整包采用 |
| 当前 `integrateCard` 会采用资源并写入登记项目的卡牌文件 | 有人工按钮，但没有统一的试玩后整包加入机制 | 所有自动写入先进入候选，正式写入只走采用服务 |
| 生图提供方已选 Codex；当前是任务复制与图片回填 | 可以协作制作，还不满足新手的自动体验 | 单列可靠生图交接能力验证，不能用提示词掩盖接口缺失 |
| 原生便笺会话已可讨论选中卡牌/资源 | 不必再做一套聊天 UI | 补齐每条消息的对象、版本、选择与试玩上下文 |
| 选择讨论目前会先运行一次“确认选中项”的模型轮次 | 导航也产生额外等待 | 打开对话只准备上下文，真正发送需求才开始制作 |
| 宿主已有 v2 候选工作区与进程管理；CardGame 仍有 v1 自管端口适配脚本 | 不能把文档里的新预览能力当作游戏已完成迁移 | 迁移游戏适配器，统一使用宿主管理的确切提交 |
| 游戏已有 WorldMap、Hub、Story、Expedition、Battle 场景及 content catalog | 可以做跨领域冒险内容 | 以稳定引用、内容注册和场景入口扩展 |
| NPC/物品有世界 seed 数据，但登记一个对象不代表玩家能遇到或使用 | 新增 JSON 不是可玩 NPC 或道具 | 增加位置、交互、条件、奖励和行为的接入契约 |
| 可玩剧情已有属性条件、选项显示/禁用及状态效果；现有图样例各 2–9 个节点，人物 seed 较基础 | 短剧情基础可复用，不能外推为长篇人物和剧情已经完成 | 增加人物/属性定义、共享事实、章节/片段、稳定对白 ID 与长篇验收 |
| Worka 当前 Markdown 剧情编译生成空 effects/onEnter，未编译选项条件；节点/选项 ID 依赖路径/序号 | 当前生成的正文分支还不能表达完整的条件剧情 | 打通规则编译和源码定位，保留稳定 ID 与迁移映射 |
| 战斗存在结构化效果与多个运行处理器，部分随机直接使用 `Math.random()` | 类型声明不能证明机制已执行，也不能据此承诺确定性回放 | 建立实际能力索引，逐步接入种子随机和行为场景 |
| 有剧情/秘境存档服务及兼容性登记 | 需要扩展已有机制 | 增加候选与正式存档隔离，不能仅靠预览端口不同 |
| 当前卡面覆盖单位卡，攻防等关键状态动态显示，但名称/部分说明已烘焙进贴图 | 是小样，不是完整卡牌展示系统 | 抽取共享布局，覆盖全部六卡种及各种游戏显示位置 |

“已有”只指代码或已记录的验证；本轮没有重新执行真实模型、全部剧情和完整战斗验收。

## 3. 桌面设计：一个创作视角，同一组便笺

### 默认创作视图

2026-09-27 收敛约束：所有便笺新增界面前，先核对现有功能能否完成操作；确有缺口时优先补共享能力。知识库先沿用 Markdown 文档、索引页和普通链接，不按原型另做人物、剧情等专用目录和筛选面板。

桌面保留项目与当前对象的必要定位；制作与采用状态由功能进展负责，不在桌面和每张内容便笺反复展示。创作视图聚焦当前打开的便笺，切换沿用现有导航。需要试玩时打开试玩便笺；需要讨论时点击便笺自带按钮，定位 **DSH 已有消息面板**中的对应会话。

Worka 的可用区域优先留给内容；试玩画面归试玩便笺。DSH 消息面板的停靠、尺寸、消息渲染、输入与窄屏交互沿用 DSH，不由创作桌面重新实现。对象选择通过现有选中态和标题表达，版本在确实影响判断的位置显示；不常驻“讨论对象”“在 DSH 中讨论”等额外说明栏。当前完整画布、连线和技术详情通过“完整桌面”进入，来回切换不丢布局、选择与 DSH 会话草稿。

这是宿主对现有便笺的一种聚焦呈现，**不再增加一张复制所有数据的总控便笺**。领域编辑继续由原便笺承担，项目摘要只是已有事实的投影。

| 用户看到的入口 | 现有归属或新增归属 | 日常显示 | 深入时才显示 |
| --- | --- | --- | --- |
| 当前想法 | 现有待办，保持唯一需求/反馈台账 | 当前想法、进度、继续对话 | 拆分任务、来源和历史 |
| 功能进展 | 现有功能进展便笺及 feature-tracker，增量扩展 | 保留功能列表、摘要、下一步及 PR/CI/部署；有可确认候选的功能项补充确认入口 | 沿用决策与记录，按需查看候选变更、检查证据、采用历史与撤销 |
| 卡牌与卡组 | 扩展现有卡牌库 | 真实卡面、套牌、获得方式、选中对象 | 定义、版本、引用与数值比较 |
| 世界 | 新增世界便笺，复用内容服务 | 大地图、据点、秘境三个视图 | 节点、路由、条件、遭遇、奖励关系 |
| 游戏内容 | 知识库及共享内容查询；实体按稳定引用打开 | 人物、剧情、游戏任务、道具、战斗与成长、经济与制作、游戏界面与引导、世界设定 | 属性/事实的引用、局部分支、条件依据、存档影响和运行定义 |
| 美术与素材 | 现有资源库；生产任务仍由 AI 资源生产承担 | 人物立绘、场景背景、道具图标、卡牌主题、声音、UI/字体、动效/过场、3D/渲染源件 | 用途、实际预览、原件与衍生、版本、生产配方、来源与费用事实 |
| 试玩 | 现有试玩便笺 | 候选运行画面及已有播放控件 | 测试入口、角色预设、版本选择、日志与运行控制 |
| 制作过程 | 现有 AI 资源生产 + 执行台 | 一句话进度和必要的待处理原因 | 子任务、错误、重试、交付历史 |

不为每张卡、每个 NPC、每次想法创建便笺。内容数量增长时依然是少量工具便笺，内部索引分页、媒体按需加载。

### 内容完整，但操作入口保持少量

默认创作视图展示功能进展、世界、卡牌库、知识库、资源库这些内容入口。待办、AI 资源生产、执行台、试玩在完整桌面保留各自独立便笺，不再在原型中把“试玩 · 资源库”“AI 资源生产 · 执行台”合成无法打开的说明块。实际迁移读取现有便笺 ID、名称和图标；世界是规划新增的领域视图，其余扩展现有对象。

知识库先用现有文档索引页和链接组织内容；资源库沿用已有分页、检索、按需加载与历史折叠。只有具体操作无法通过现有入口完成时，才补共享查询或组件。不把所有属性、格式参数和制作步骤常驻；原型的少量样例不能替代规模实现。

| 内容归属 | 覆盖对象 | 必须连通的关系 |
| --- | --- | --- |
| 卡牌库 | 六类卡牌、卡组、收藏/解锁、初始套牌、敌方卡组、获得方式、主题 | 定义与卡图分离；卡组引用卡牌；主题覆盖全部显示位置 |
| 世界 | 区域、据点、秘境、入口/出口、传送点、交互物、碰撞/寻路、遭遇、时段/天气 | 场景逻辑引用背景/层/音景；正常游玩可到达并返回 |
| 知识库 · 人物 | 主角、同伴、NPC、敌人，能力/特长、关系、知识、动机、成长、队伍 | 定义与存档实例分开；能力与事实影响剧情；立绘、头像和声音引用独立 |
| 知识库 · 剧情与游戏任务 | 章节、场景、对白、旁白、选项、分支、结局、伏笔，目标/阶段/失败/重复规则 | 台词 ID 关联配音/字幕；任务操作物品、人物和共享事实；与创作待办区分 |
| 知识库 · 道具 | 消耗品、装备、钥匙/工具、任务物品、合成材料、货币；按需扩展容器 | 获得、堆叠、持有/装备、使用/消耗、交易/丢弃、任务检查、存档和表现 |
| 知识库 · 战斗与成长 | 技能、效果、增益/异常、触发器、能力检定、敌人行为、遭遇、经验与队伍 | 规则事件驱动音效/动效；有边界案例、费用、目标与结算顺序 |
| 知识库 · 经济与制作 | 商店、采集、掉落、奖励表、合成配方、价格/库存/补货与资源循环 | 钱款、库存、容量、材料与产物一致更新；首次奖励不重复 |
| 知识库 · 游戏界面与引导 | 开始/继续、存档、设置、对话/回看、背包、战斗 HUD、教程、输入与无障碍 | 行为与 UI 皮肤分离；空/忙/错/禁用态可读；键鼠/触控适配 |
| 知识库 · 世界设定 | 阵营、历史、地点、术语、时间线、正史/传闻、人物知情范围 | 保留来源与有效章节，为局部写作提供相关上下文 |
| 资源库 | 图像、声音、UI/字体、动画/过场、3D 源件及衍生文件，见第 8 节 | 同一素材可被多处引用；按版本定位影响，不能只显示文件名 |

原型用“止露草 → 寻药委托 → 狐爷爷/剧情 → 图标/拾取音效”和“灵狐护佑 → 卡牌 → 护盾动效/战斗音效”演示这种关联。内联对象链接用于定位相关内容，不承担对话、试玩或采用。素材详情中的原图/试听/逐帧检查是资产检查；候选游戏的运行和游戏混音仍只在试玩便笺。

### 功能进展统一收口

沿用现有功能列表、搜索、筛选、展开/折叠、归档、决策与记录，以及 DEV/PRE/MAIN 的合并、CI、CD 展示。compact 仍是现有摘要视图。游戏工作流接入同一功能项，不将整个便笺改为新的交付页面，也不要求先重构功能进展才能启动其他工作。

最小扩展是：工作流在现有摘要、下一步和记录中补充必要变化，保留用户已有记录；对应功能项存在经过验证的候选时，按需展示候选版本与“加入我的游戏”；采用历史、检查详情和撤销在该功能项展开的记录中查看。制作中或存在缺项时用下一步说明原因，不常驻完整流程、素材清单和多组操作。实际确认复用宿主现有确认方式，不增加常驻确认页面。

一个功能项代表一次可独立验收的游戏变化，可以是一张卡，也可以是包含地图、NPC、剧情、道具和规则的冒险。功能进展汇总同一份候选清单并提供确认加入及记录/撤销；用户在试玩便笺体验对应版本后回到这里确认，不增加第二套试玩控制。不默认一次采用整个项目的所有待办。

现有功能 ID、名称、图标与会话保持不变。待办保存需求与反馈，生产/执行服务保存过程事实，试玩服务保存运行版本；功能进展通过引用聚合，不复制出另一套私有进度。权威功能记录仍由 feature-tracker 维护，游戏采用事实由采用服务提供。

功能进展按当前事实表达“内容已制作”“可以试玩”“验收未完成”“待确认”“已加入源码”，复用下一步与记录，不把这些状态同时画成新流程栏。现有 PR 合并、CI、部署继续独立展示；未登记 PR 不阻止一个已验证的本地候选进入采用确认，PR 合并也不等于游戏内容已验收。服务不可用或证据过期时不可用缓存伪造可交付状态。

功能进展按 `featureId` 关联产物和候选，用户通过现有桌面导航打开它。需要核对归属时在关联详情中展示真实引用，不给所有内容页加固定跳转按钮。同一对象关联多个功能项时显示实际关联，不能靠名称猜测或自动选择全部。后续修改已加入的功能，生成该功能的新候选并重新确认，已采用版本及记录保留。

### DSH 消息面板成为唯一对话入口

一张卡可以通过便笺自带的会话按钮说“这只狐狸再弱一点”；地图上选两个点可以说“这里加一条捷径”；在试玩便笺体验后可以说“刚才这关太难了”。内容便笺只保留与当前对象相关的选择、比较和简单编辑；重试归实际失败步骤，试玩归试玩便笺，采用与撤销归功能进展。

每次发送消息都绑定一个上下文快照：当前便笺、项目、创作事项、对象引用及 revision、明确的选中集合、候选版本；试玩场景再包含场景/节点/回合/种子/检查点。必要的上下文核对沿用 DSH 支持的附件/对象展示，用户可以清除或切换；内容区域不额外复制一条讨论上下文栏。若宿主缺少对应能力，扩展原生入口的共享协议，不新增业务按钮。

对象绑定必须发生在消息发送时；切换选择不能改写已经发送消息的目标。AI 执行前重读版本，过期时重新比较，不用会话里记住的旧数值直接覆盖。

全局想法默认进待办原生会话；针对领域对象打开该领域原有会话。跨领域子工作关联同一个创作事项，用户不用跟着切换多个聊天。试玩反馈仍回到原待办或其子项，不建立第二份反馈库。

实现复用便笺自带按钮的现有打开会话链路，选中对象通过宿主公开上下文协议接入。已有 `ctx.agent.prepare` 与 `workbench.openSession(sessionId)` 能力仅在共享链路内按需复用，不以它们为理由增加“讨论”按钮。消息发送、会话历史、模型选择、凭据、运行与取消都由 DSH 负责。只打开面板或切换选择不得先调用模型“确认选中项”；不把对话复制进便笺 state。

首次打开只给“说说你想做什么”和少量真实例子。AI 默认先做一个小而完整的版本；只有会明显改变结果的歧义才问，优先一次一问。暂定选择记录在任务中，用户随时一句话修改，无需填项目配置表。

### 状态与异常要能读懂

用户状态：`正在理解 → 正在制作 → 可以试玩 → 等你确认 → 已加入游戏`。需要处理时用“需要你选一下”“正在修复”“暂时做不到这个步骤”，同时说明已保留什么、下一步是什么。

“已生成图片”“服务已启动”“检查通过”“已经加入游戏”是不同事实。没有检查不能显示通过；未知费用不能显示为零；进度用真实完成项，不伪造百分比或倒计时。

## 4. 用一段冒险贯穿体验

示例输入：

> 我想在青云外山加一片雾林，有个卖药的狐狸老爷爷。帮他找回药草后，可以得到一张会保护同伴的灵狐卡。简单一点，十分钟能玩完。

以下内容数量是规划样例，不代表系统现在已生成。

1. AI 读取已有世界设定、卡牌和玩法能力，形成一段简短的“我会这样做”，自动建立创作事项。十分钟是设计目标，最终记录真实试玩时长。
2. 自动组合一张小秘境、一个可互动 NPC、一段有分支的事件、一件任务物品、一张奖励卡、一个遭遇和可返回的出口。角色名称与外观保持一致。
3. 每个对象同时定义“在哪里出现、怎样获得、如何使用”。卡牌接到任务奖励与测试卡组；NPC 接到地点和对话；药草接到获得、交付和消耗；地图接到已有世界入口。
4. 用占位资源先检查玩法与路由，同时生成所需插画；后台完成资源登记、卡面组装和替换。占位版本可以提前玩，但明确标记尚未完成美术。
5. 自动检查引用、剧情分支、任务奖励只发一次、卡牌行为与退出路径。启动冻结版本，默认从雾林入口进入，另有“从游戏开头玩”。
6. 用户说“爷爷别那么严肃，护盾太强了”。系统改对应人物文本/图像要求及卡牌数值，保留已确认的地图与其他素材，产生下一候选。
7. 用户回到功能进展中的“雾林遇狐”功能项，查看“新增雾林、狐爷爷和奖励卡，修改青云外山入口”及存档兼容情况，统一确认加入。确认绑定刚才试玩的确切版本。
8. 整包应用、相关验证通过，功能进展记录采用版本并提供撤销。正式游戏从正常入口能够到达这段冒险，玩家不需要调试按钮。

用户不承担 ID 命名、资源导入、文件上传和修复脚本。真有缺失能力时，系统明确阻塞原因，不能要求孩子成为管线操作员后再宣称自动化完成。

此例需要升级为人物与剧情能力的验收切片：口才影响说服选项，洞察揭示线索，医术和道具决定救治方式，人物关系及守密/告密决定下一章的回应；低属性仍有明确的其他路线。具体条件和测试主角见[长篇方案第 5 节](cardgame-narrative-system-plan.md#5-用雾林遇狐检验复杂度而不只演示发奖励)。不能以只有“接受/交还/再交谈”的三句演示代替验收。

## 5. 一条共用流程，按内容类型选择配方

共用流程：**理解与范围 → 内容/代码草稿 → 素材与组装 → 自动检查 → 隔离试玩 → 对话迭代 → 用户确认 → 加入源码**。

内部是有依赖的步骤图，界面保持简单。数值改动可以跳过生图；换卡面可以复用卡图；机制改动必须走代码及行为检查。先用少量代码定义配方，不建设让用户拖节点的通用流程编辑器。

现有逐卡 `approveCardDrafts` 人工闸门需要重新划分：后台“固定本轮草稿版本”与“用户明确认可/锁定某项设计”是两个事实。默认自动流转到候选试玩，不要求用户逐卡确认每个阶段；AI 自选候选只在试做范围内生效，不能记录成用户已经批准。人工微调与锁定随时插入，最终加入源码的用户确认始终保留。

| 用户想做什么 | 系统应一起交付什么 | 必须能试玩什么 |
| --- | --- | --- |
| 一张卡 | 合法定义、效果实现引用、插画、主题布局、获得位置、测试场景 | 获得/抽到、打出或使用、触发效果、数值与说明相符 |
| 一套卡组 | 卡牌依赖、重复数量、组合说明、明确的初始牌组/遭遇入口 | 真实牌序规则下的一局；不把强度估计当平衡结论 |
| NPC/主角 | 人物设定与本局状态分离；按需组合能力、身份、关系、知识、成长、持有物和出场引用 | 属性门槛、关系/知识分支、人物反应、重复访问及跨章持续；路人不强制填完整属性表 |
| 道具 | 类型/用途标签、图标、持有与实例规则、堆叠/装备/使用/消耗、获得/交易/丢弃、剧情与音效引用 | 获得、使用、扣除、效果、满包/无效使用、装备修正与存档；工具检查不误消耗，任务物不误售 |
| 游戏地图 | 世界路由或据点空间或秘境拓扑、表现资源、遭遇/事件/奖励、入口与出口 | 从已有入口到达、完成目标、离开并保留结算 |
| 剧情/游戏任务 | 章节/场景/对白片段、稳定 ID、条件与结果、任务阶段、人物弧线和跨章事实、可编译内容 | 主要与备选路线、门槛边界、隐藏/锁定选项、失败/重访、奖励幂等、跨章续接和长篇局部修改 |
| 一个机制 | 规则示例、运行实现、数据契约、显示反馈、确定性场景和兼容影响 | 实际触发、边界与反例；不只生成说明文字 |
| 一组场景素材 | 背景/前后景、放置与裁切、图层、地图物件及音景，明确引用位置 | 多尺寸下人物/交互可见；遮挡正确；场景切换无漏载和残留 |
| 声音或配音 | 原件与运行编码、循环/切片、事件或对白绑定、混音轨与版本 | 场景进出、事件触发、字幕、静音/缺文件降级与无叠播 |
| UI / 游戏主题 | 可交互组件、皮肤/字体/图标、布局规则与状态；必要菜单和引导 | 长文、禁用/失败/忙碌态、输入焦点、触控、音量/字幕设置 |
| 动画 / 3D 表现 | 实际需要的源件、动作/锚点/时间事件、转换配方与运行输出 | 时序、碰撞/遮挡、资源释放、性能预算与低性能降级 |
| 一个新游戏 | 项目母版、主循环、首个章节、角色与内容包、教程/菜单/存档、美术方向、独立构建 | 新玩家从开始到目标、失败恢复和再次进入 |

世界地图、据点空间、秘境节点图分别保留自己的语义。不能用一张爬塔图代替所有地图，更不能把地图背景画好了视作导航与交互已实现。

## 6. 游戏本体：建设可被可靠创作的运行基础

### 6.1 统一内容边界，复用 content catalog

在现有 catalog 和解析/验证代码上增加类型适配器：每种内容提供读取、校验、引用枚举、影响分析、试玩入口和可用操作。稳定的领域 ID、资源 ID、磁盘路径继续区分，不把名称作为身份。

卡牌、人物、物品、地图、遭遇、商店、事件、规则都进入可查询的能力与引用范围。第一步统一校验和引用，旧文件可以通过适配器继续读取；不要求一次搬迁所有文件。

明确每类内容的创作源。卡牌等结构化 JSON 是行为权威；普通 Markdown 是设定与叙事资料；声明为可编译场景的 Markdown 才产生运行剧情数据，生成文件标记来源，禁止双向编辑造成两份真相。人物设定和运行 NPC 通过 ID 关联，不能各自长出独立版本。

维护可自动生成的“当前可做能力”：运行时已实现的效果、条件、触发器、对象类型、可用资源配方和预览入口。只出现于 TypeScript 枚举或设定文档的能力不能标成可用。

### 6.2 区分数据创作、现有机制组合、新机制开发

- 数据创作：改名、数值、地图节点、现有条件和奖励，使用类型化领域命令。
- 机制组合：将已验证的触发器、条件、动作组合成新卡/事件，校验组合和执行语义。
- 新机制：现有运行时无法表达时，明确进入源码开发配方，在候选工作区实现处理器、UI、内容类型及测试。

例如“保护左边的同伴一次”需要先确定目标选择、持续时间、消耗时机、叠加规则与死亡后的行为。系统从例子推导规则，必要时问一个有玩法意义的问题，不能偷偷替换成文字相似的旧效果。

优先补齐已有事件/效果链的执行一致性；确有重复再抽取共享核心。自定义机制走已登记的代码模块，不在游戏数据中塞任意可执行脚本。

### 6.3 从场景中抽出可测试的玩法逻辑

逐步让规则接收明确状态和动作，返回状态变化及领域事件；Phaser 场景负责输入、动画和展示。无需一次重写所有 manager，先处理新机制依赖的路径。

为影响玩法的随机源提供可注入种子，记录动作序列；纯装饰粒子随机不进入玩法结果。现有直接随机调用需逐条迁移，未迁移的路径不标“可重放”。机制测试尽量不依赖截图和动画时序。

### 6.4 统一表现系统和卡面主题

把“规则定义、运行状态、美术资产、展示模板、用户外观偏好”分开。主题只影响展示，不改变卡牌身份、攻防和效果。

共享展示契约供真实游戏和 Worka 预览消费，规定六卡种的插画窗、裁切、名称/说明区、图标、动态值、长文案策略，以及手牌、战场、卡组、详情四种使用场景。现有 SVG 卡面配方可迁入这个契约；游戏仍使用现有 Sprite 工厂扩展。

布局使用声明式槽位、约束和版本，避免把每个主题做成任意可执行组件。青玉与宣纸保留为两份真实模板，新增模板由 AI 修改规范并生成代表性样本供比较。

项目默认主题、系列主题、单卡选择、玩家本机外观偏好采用明确优先级：`玩家偏好 > 单卡 > 系列 > 项目默认 > 内置回退`。玩家偏好只选择兼容的现有模板；项目默认的修改进入候选，不静默改源码。

静态底图可缓存；游戏中的即时攻防、境界、状态、临时规则文本由运行状态绘制。完整导出图只作缩略图/分享，不能成为战斗状态的来源。固定字体及其可分发版本，跨系统长文案溢出应给出诊断。

### 6.5 游戏预览与反馈桥

游戏提供开发预览模式：按 card/deck/NPC/map/story/scenario 的稳定引用启动；加载明确的初始状态或检查点；报告当前候选指纹、场景、对象、回合及最近关键事件。

预览桥只允许已登记的动作，如进入场景、重开、读取简化状态、导出测试存档；验证来源、会话能力与消息结构，不暴露任意脚本执行。正式发布关闭调试写入入口。

用户反馈“刚才这张太强”时附带当前卡的实际临时状态和相关事件；无法确定对象时让用户点选，不凭截图或文案猜测。回放保存有界事件记录和版本引用，避免收集全量历史。

### 6.6 存档与版本

扩展现有 SaveCompatibility、StoryHubSessionPersistence、RunPersistence，统一 project/candidate/profile 的存储命名空间。预览重用端口、两个候选并行运行和重新打开浏览器，都不能串正式存档。

每个采用包声明对旧存档的影响：兼容、需要迁移、仅新开局可体验。新增机制改变存档结构时交付对应迁移和回退限制；不能自动清空用户存档来让测试通过。

### 6.7 人物、任务与共享叙事事实

采用一套可组合的人物模型：人物定义保存身份、人设、初始能力与表现引用，本局状态保存成长、关系、知识、物品和剧情经历。主角在共用基础上增加玩家成长、队伍及关键选择。路人只启用所需部分；默认人物页只展示简介、关键能力、关系及相关剧情，通过 DSH 对话深入修改。

扩展已有条件求值器，让事件触发、选项可见、选项可选和选择后果表达不同语义，首版默认明确的数值门槛。属性目录、条件证据与自然语言解释共用一份规则；未知字段不能静默当零。复杂随机/对抗检定仅在有实际玩法需求时加入并记录结果。

扩展现有 GameWorldState 与存档 owner，明确跨章节人物和世界事实的权威服务；会话仅保存局部阅读位置与临时状态。同一人物从不同入口出现时，关系和已知秘密不能变成互不相干的副本。游戏任务是玩家的目标/阶段，Worka 待办是作者的创作事项，两者关联而不共用完成状态。

### 6.8 长篇写作与运行容量

正文按“作品 → 章节 → 场景 → 对话片段/选择”组织。章节和人物先由普通 Markdown 索引页及链接定位；长场景按对白分页阅读，确有定位缺口时再补通用文档搜索。不展示全书所有台词的巨型节点图。一千句对白不等于一千个选择节点；支持局部分支汇合、条件对白和可复用片段，保留有意义的后果。

扩展现有 Markdown 源与编译服务，补齐条件/结果编译、稳定的场景/对白/选项 ID、源码定位、章节包和依赖索引。发布/首次校验覆盖整个内容包，编辑时只重编受影响内容，运行时按场景需求加载和复用索引。AI 按场景读取原文、相关设定及有版本的依赖，不靠一次塞入整部小说维持一致性。

首档长篇验收目标为 30 万有效正文字符、20 章/20,000 条对白、200 人物及 3,000 选项，另验收一章真实编写内容。它们是待测目标；性能、跨章存档和分支覆盖未验收前，不宣称现有系统能可靠承载。完整测试方法见[长篇方案第 9 节](cardgame-narrative-system-plan.md#9-容量与正确性必须有独立验收)。

## 7. Worka 后台：可恢复的创作事务

### 7.1 一个事项，多个现有业务记录

新增轻量“创作变更集”契约，以现有 `featureId` 为交付归属，关联待办、制作批次、资源版本、执行任务、预览候选与采用回执。它持有依赖和版本，不拥有第二份任务调度、聊天历史或资源数据库。功能进展扩展公开查询来聚合这些引用，不用便笺 state 替代权威记录。

| 记录 | 关键事实 | 权威归属 |
| --- | --- | --- |
| 游戏档案 | 母版、主循环、世界/美术决策、默认规则和预算偏好 | 项目文件；模型凭据仍归宿主 |
| 创作事项 | 原始 idea、目标、范围、验收、来源上下文、人工锁定项 | 现有待办扩展 |
| 功能项 | 稳定功能 ID、标题、关联创作事项和候选/采用引用 | 现有 feature-tracker；功能进展为统一交付界面 |
| 制作计划 | 有依赖的步骤、输入指纹、产物引用、失效原因 | cardgame workflow 扩展 |
| 工作区基线 | 仓库、基线提交、允许纳入的未提交修改快照、内容版本 | 宿主工作区能力 + 游戏创作服务 |
| 候选清单 | 代码/数据/资源/模板/能力版本、入口、测试存档、检查证据 | 不可变候选产物 |
| 采用记录 | 用户确认的清单指纹、目标基线、实际变更、验证、撤销信息 | 游戏采用服务 |

模型负责计划与创造；确定性服务负责校验、版本、保存和授权边界。不能靠一句“不要修改正式文件”的提示词实现隔离。

### 7.2 所有自动写入都绑定候选范围

先建立明确的 `projectId + workspaceId + proposalId`，绑定到当前执行上下文与资源查询。普通便笺配置不允许通过任意路径授予写入权限；制作命令不能回退到正式项目目录。

需要统一检查的现有入口包括 `updateCard`、`savePipelineCard`、`compileStory`、`adoptVersion`、卡面主题默认值，以及执行台写文件工具和自动编译监听。跨便笺跳转也必须携带候选范围，不能前端显示“草稿”，后端仍在写正式文件。

候选索引和文件监听按工作区分区。正式项目的人工外部修改仍可被索引发现，但只产生基线变化提示，不把当前候选偷偷应用回去。

候选开发工作区可变；用于试玩的快照不可变。冻结时在系统自有范围生成确切提交/资产清单，再交给宿主 v2 预览。现有 `HEAD+worktree.<hash>` 字符串不能当成可检出的 Git 提交。

用户本来存在的未提交修改必须保留。纳入候选的文件按项目范围和排除规则快照；不要混入凭据、运行数据库或依赖目录，不要求用户先提交，也不自动重置主工作区。

### 7.3 步骤可靠性

每一步保存输入指纹、依赖版本、产物引用、状态与实际错误。失败只重做受影响步骤；已经完成的图像和检查不会因为页面关闭而丢失。

传输重试复用 requestId；外部任务另存 providerJobId，不确定是否提交成功时先查任务，不能直接再付费提交。并发 worker 使用租约/版本校验，防止同一步执行两次；正式应用按项目串行。

取消阻止后续步骤并尝试取消外部任务；无法取消时显示真实状态，返回结果保留为未采用候选。恢复时从持久事实继续，不能从前端的进度条推断完成。

修复有次数、时间和费用上限。纯格式/装配错误可自动修复；超限呈现一个有上下文的决策。关闭便笺不等于停止任务；关闭宿主后如没有已接通的远程执行能力，只能暂停并在下次打开继续。

事实事件用于刷新依赖与失效状态，不能把每次索引更新都变成无界模型运行。明确的创作请求授权该次有限流程，巡检只提供诊断或既有授权范围内的修复。

## 8. AI 素材生产与成本

### 8.1 生成方式与能力边界

默认由 Codex 生图，保持用户已经选定的方式。优先完成静态 2D 配方；游戏确实需要多视角或可复用动作时，再验证 3D 建模与渲染配方。素材和卡面布局独立，数值/规则调整不重复生图。

风格档案包含参考图、构图、色彩/材质约束、角色身份锚点、目标尺寸和不希望出现的内容，随项目版本保存。卡图、NPC 立绘、地图背景和物品图标分配方，不能拿一个提示词兼顾所有输出。

**生图交接是首要技术验证项。** 当前内置工具存在于本 Codex 会话，不等于 Worka 获得远程调用权限。验证目标是通过受支持能力完成“提交已固定请求 → 在授权执行端生成 → 自动登记原件与元数据 → 唤醒后续组装”，不抓取会话、不假设隐藏 API。

能力探测需区分：可自动执行、需要显式进入 Codex 交接、不可用。开发期可保留现有复制/回填入口；面向新手的正式版本不能将这条人工接力计为通过。如果无法使用用户指定的自动能力，保留已完成方案和占位试玩，明确需选择支持的执行方式，未经同意不换收费服务。

首轮默认少量候选与有限返修，优先复用已有素材。显示实际调用/候选数量；有可靠价格时展示估算及实收，否则标“费用未知/使用账户额度”，不虚构金额。预算在首次设置或超额时处理，正常制作不反复审批。

声音、动作动画和 3D 均有各自能力验证。静态图不等于 spritesheet，渲染图不等于可绑定模型；未接通的必需素材阻止相应完整交付。发布资源记录来源、加工步骤、字体和使用许可资料，避免交付只在作者机器可用的资产。

### 8.2 资源库的完整覆盖

资源库是同一个入口，不按“每种格式一张便笺”拆分。按用途默认给出合理规格，用户通常只需要说“雾浓一点”“狐狸受伤的表情别太夸张”“音乐再安静些”。技术格式和加工参数只在详情中出现。

| 分类 | 具体内容 | 制作与加工 | 接入及验收重点 |
| --- | --- | --- | --- |
| 人物与立绘 | 角色参考、头像、半身/全身立绘、表情、姿势、服装变体、探索小人 | 基准图确认后派生；透明底、裁切、尺寸与锚点一致 | 身份一致、表情/服装键、对话安全区；小人动作不是静态立绘 |
| 场景与背景 | 远景/中景/前景、室内外背景、昼夜天气、地块、场景物件、小地图与地点标记 | 分层、透明遮罩、无缝地块、必要状态与目标显示尺寸 | 碰撞/遮挡/导航另外建模；与交互、镜头和区域音景一起检查 |
| 道具与图标 | 物品、装备、材料、货币、技能、状态、任务标记、操作提示与光标 | 统一轮廓/光源/留白，独立源图与图集 | 小尺寸辨识、文字外置、稳定键与反向引用；不用一张拼图代替图标集合 |
| 卡牌插画与主题 | 插画、边框、卡背、稀有度图标、材质、六类卡牌布局 | 先图后模板组装；保留源件；派生不同尺寸展示图 | 动态数字/文本、长说明、无图回退、所有显示位置一致 |
| 声音 | 音乐、环境循环/随机声、UI/交互/战斗音效、对白/旁白配音 | 原始母带、剪辑/循环点、混音、电平、运行编码；生成能力待验证，支持导入 | 音乐/环境/音效/配音分轨；切换渐变、并发上限、重复触发与播放失败降级 |
| UI 与字体 | 界面主题、面板/九宫格、按钮/背包格/提示/血条、字体、游戏图标/标题封面/加载页 | 代码组件负责布局/状态/交互；图片负责装饰，字体保留文件与使用资料 | 常态/聚焦/选中/禁用/忙碌/错误，中文缺字、长文、本地化、窄屏和离线打包 |
| 动效与过场 | 程序动效、粒子、序列帧/图集、角色动作、镜头、过场时间线、可选视频/字幕 | 优先复用程序效果；需要时生成帧、绑定时间事件或输出视频 | 帧连续、锚点、命中同步、循环、清理、跳过/回看、减少动态效果与性能 |
| 3D 与渲染源件 | 模型、UV、材质贴图、骨骼/蒙皮、动作、灯光/相机、场景与渲染配方 | 按需验证建模/绑定/渲染；源件与运行交换格式分别保留 | 拓扑/关节/贴图、坐标比例、性能、可重复渲染；2D 输出不冒充完整 3D 资产 |

2D、3D 再渲染是生产方法；立绘、图标、卡图是用途；PNG、WAV 等是格式，不能用单个类型字段混合这三个维度。首版以静态 2D、现有/导入声音、代码 UI、少量程序动效完成一段游戏。全配音、复杂骨骼动画、实时 3D 和视频只在具体 idea 需要时进入范围；不因目录列出它们就默认生成全套。

### 8.3 同一份资源，从需求到游戏引用

复用 cardgame-library 的 assets/media/versions 查询、现有稳定内容引用、MediaCapabilities 的受限文件地址和生产 request/receipt。当前已有图像、音频及序列帧相关展示，**并不代表音频生成、3D 预览、字体处理和所有生产器已接通**。新增类型通过相同查询契约扩展，不再建平行资源库；3D 等不能直接通过当前媒体接口的类型，先提供元数据与已生成预览，支持后再增加受验证适配。

需要补齐的关系是：创作事项/功能 → 素材需求 → 制作任务 → 资源原件/版本 → 衍生文件 → 游戏使用位置。需求尚未产生文件时是 requirement，不伪造 ready asset。现有资产 ready/candidate 与生产步骤状态分别保存；“索引就绪”也不等于“已通过游戏验收”。

每份实际资源保留稳定身份、用途标签、来源/许可资料、版本校验、生成或导入记录、加工配方、实际规格、派生关系和引用位置。图片按尺寸/裁切/锚点验证，声音按实际时长/循环/电平验证，动画按帧和事件验证，UI 组件按状态/布局验证，模型按源格式与运行契约验证。没有实际文件，不显示虚构缩略图、波形、试听或成功标记。

变体沿用同一角色/场景身份：表情、服装、昼夜、语言和分辨率分别建变体键。缓存键包括源件和配方版本。只改物品数值无需重画图标；修改台词只使对应语言的配音/字幕衍生失效；更换立绘基准需要检查相关表情，不能悄悄把所有正式版本替换掉。删除前查询引用；已采用的资源保留到存档/构建不再依赖它为止。

生产结果先进入候选清单，经组装自动登记到试玩。卡牌、人物、场景、任务只存资源引用，不私自复制文件路径和媒体数据；发布阶段收集确切版本的依赖闭包并生成持久本地资源包，不能依赖临时 URL。

### 8.4 系统负责检查遗漏

每个配方自动检查六类需求：**玩法内容、画面、声音、界面/操作、存档/兼容、入口与退出/验证**。检查的是“此次变更是否需要、是否已有可复用、还缺什么”，不为一张卡强行制作菜单或整套背景音乐。缺少信息时优先继承项目风格和已有默认值，只把影响玩法方向或费用的必要选择交给用户。

例如“加一瓶治疗药”应一起补足物品定义、获得/购买入口、图标、使用和消耗、成功/失败反馈、背包满/生命已满、存档与受影响检查；如果现有音效和背包 UI 足够就复用。新增 NPC 则补身份/出现地点、剧情条件、立绘/头像、交互、任务与后续影响；配音是明确的可选项，不让它卡住无配音版本。

功能进展只按该功能的必需依赖判断能否采用。允许带清晰标记的占位候选供早期检查，但完整交付不能把尚缺必需美术、运行接入或检查证据的版本标为待确认。可选资源不阻断当前范围；用户后来要求全配音时，把配音加入新功能范围并重新验证。原型因此区分“雾林遇狐：素材未齐”和“灵狐卡面主题：确认交互示例”，避免无关素材混入一次采用。

## 9. 预览与确认：采用的必须是刚才玩的版本

### 三层预览

1. **对象预览**：卡面、人物、物品、地图布局，快速调整外观。
2. **行为预览**：固定起点的短场景，验证出牌、交互、奖励、机制。
3. **正常游戏路径**：从菜单/既有地图入口到达新内容，验证结算与保存。

每个制作包按实际范围提供对应层级。只改卡面无需把无关剧情重测；加入新地图则必须覆盖其路由和出口。新增内容即使在调试入口可见，正常玩家不可达也不能标记完整完成。

正在玩的版本固定，新的制作结果显示“有新版可试玩”；切换发生在明确重开/检查点，不在一局中替换规则。占位素材版本和完成版分别标识。

### 采用协议

采用前在功能进展的对应功能项内显示面向用户的摘要：新增了什么、改了哪里、能否继续旧存档、哪些检查尚未覆盖。技术 diff 和资源清单可以展开；其他便笺不复制交付按钮或固定跳转栏。

确认绑定 `featureId + candidateHash + targetBaseRevision + validationManifest`；DSH 消息面板里的“就用这版”可以触发功能进展所用的同一交付动作，但必须有唯一、可见的功能项和版本上下文。泛泛的“好看”不触发源码写入。后端校验该功能项与候选的归属；内容便笺不保留绕过它的正式写入动作。

采用过程：

1. 重新核对正式源文件的基线与外部变化，计算完整依赖闭包；有关联依赖的对象成组加入。
2. 目标变化若造成冲突，AI 提出合并后的新候选并重新检查，旧确认失效。不要让孩子手动解决 Git 冲突。
3. 采用服务持有项目写锁，保存变更前镜像与应用日志，应用数据、代码、资源、catalog 和主题引用。
4. 文件系统的多文件写入不是天然原子操作：使用预备/应用/验证/完成的持久日志，崩溃后继续或恢复；正式构建不能读取半完成包。
5. 执行受影响的最小检查，记录最终源版本。重复点击识别同一采用记录，不重复添加卡牌、发奖励或创建版本。
6. 在功能进展内提供撤销本次加入及回执；用反向变更保留后来修改，遇到冲突生成恢复方案。不能用便笺 state 回退或 `git reset --hard` 冒充项目回退。

采用成功与远程发布分开。加入源码不自动 push、部署或覆盖已经公开的游戏；“发布这个版本”是另一项明确动作，复用同一不可变清单与验证证据。

## 10. 发布所需的体验与工程门槛

### 新用户第一次使用

安装后自动检查运行环境与已连接能力，以一个明确的下一步解决缺失项。模型账户/授权可由配置者先完成；体验测试必须分别记录“从全新安装”与“已经配置完成”，不能把前者的困难藏掉。

示例游戏可立即试玩，用户能复制为自己的项目，再说第一个想法。示例本身离线可玩；创作服务需要网络时给出真实状态。

### 发布游戏

首个发布目标选择独立 Web 构建，复用现有运行环境；其他平台另设验收。打包从已经采用的确切版本执行，包含固定资源和字体，不依赖临时媒体链接、localhost 或 AI 密钥。

交付至少包含开始/继续/重开、基础教程、操作提示、设置、正常获得内容的入口、胜负或阶段目标、存档恢复与错误反馈。手机/平板先明确目标设备与操控，不能把 1920×1080 画布按比例缩小就称为触屏可玩。

在干净环境检查构建运行、资源缺失、正常路由、基础存档和更新兼容。发布失败保留上一个可玩包；创作桌面的更新也要验证旧项目、便笺身份和任务恢复。

### 面向 10 岁使用者的验收标准

以下是**目标，尚未实测**：

- 首次进入已配置桌面后，30 秒内能找到说想法和试玩入口。
- 做一次小内容创作，除表达想法、必要选择、试玩与最终确认外，不要求用户承担技术步骤；不会要求填写 JSON、路径、端口或 requestId。
- 用户在最多三次有意义的创作决策后能开始目标场景的试玩；等待时间另行真实计量，不计作用户决策。
- 能通过原生对话完成一轮“制作 → 修改 → 试玩”，能辨认“试做版”和“我的游戏”，能独立撤销一次采用。
- 进行至少 5 位此前没用过产品的目标年龄体验测试，目标至少 4 位独立完成上述核心任务；记录卡住的位置和介入次数。实际对象与同意安排由产品测试组织，不能用成人工程师演示代替结论。
- 包含失败和恢复任务，不仅演示顺利路径；儿童理解状态文案是否正确需要观察验证。

不承诺未经验证的生成时长、成功率或玩法趣味。先测量 idea 到可试玩的总时长、人工介入次数、失败恢复率、合格产物成本和用户完成率，再决定优化顺序。

## 11. 分阶段交付与停止条件

按可验证的里程碑推进，不用虚构日程掩盖生图、源码采用和新机制的不确定性。

| 阶段 | 具体交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| M0：确认能力与基线 | 记录当前项目快照；验证 Codex 图像自动交接；梳理正式写入口；固定最小冒险验收脚本 | 生图能力实测结论清晰；候选/正式的读写边界有可执行方案 |
| M1：一个安全的完整循环 | 单位卡通过原生对话进入独立候选；接入真实获得/测试入口；功能进展统一采用与撤销；冻结版本与存档隔离 | 未确认时正式源码零变更；所有内容关联同一功能项；确认版本与试玩一致；外部并发修改、中断恢复通过 |
| M2a：人物与复杂小冒险 | 世界、NPC/主角、道具、条件剧情、任务、奖励卡、遭遇及背景/立绘/图标/基础声音/UI 一起接入；优先支持单位/法器/符箓；默认创作视图接真实数据 | 能力、关系和知识真实影响剧情；高低属性路线、道具边界、重复奖励与跨场景事实通过；画面/声音/UI 可用；新手无需素材接力 |
| M2b：一章体验与长篇基础 | 500–1,000 条真实对白的章节创作、局部修改、章节包与索引；跨章人物/任务/存档；长篇压力样例 | 本文 6.8 及专项方案的容量与正确性有实测证据；实际阅读与修改保持简单；无法覆盖的路线明确报告 |
| M3：新机制与全面卡牌 | 机制能力登记、确定性测试、规则与表现同步；覆盖六卡种；完善卡面主题与主体风格一致性 | 一个当前不支持的新机制能实现、试玩、采用、回退；既有关键行为不被破坏 |
| M4：从游戏 idea 创建项目 | 母版初始化、主循环与内容组合、引导和项目风格档案；多个创作事项的依赖/冲突处理 | 新项目走完一段独立游戏循环；原项目不串数据、不串存档 |
| M5：可交付版本 | 新环境安装、自动能力配置引导、独立游戏构建、发布与恢复、真实新手测试 | 创作桌面交付门槛与游戏交付门槛分别通过，才声明可发布 |

M0 的结果可能调整自动生图接入方式；这不阻止候选隔离开发，但会阻止宣称端到端新手体验完成。M1 未通过之前，不批量扩张更多内容类型和后台自动写入。

首个对外可演示版本可以以 M2a 为边界，明确只支持已经验收的玩法和卡种；长篇剧情创作声明必须等待 M2b。正式“孩子能独立做出游戏”的宣传以 M5 的真实测试为准。

建议下一个实施批次先完成 M0 + M1，并在契约设计时纳入人物、场景与对白的稳定身份。第一张验收卡继续使用青云山灵狐，复用已确认美术，集中验证对话、真实游戏入口、版本与采用边界；随后按专项方案 N0–N3 完成人物条件场景、真实章节和长篇基础，不把三句 NPC 对话当成完整叙事系统交付。

完整类型目录现在就纳入信息架构与需求检查，但按里程碑交付实际能力。声音生成、全配音、视频和 3D 适配各有独立能力门槛；可导入素材和 2D 路线可先完成母版，不把未验证的自动生产器承诺进首版。

## 13. 必须通过的回归场景

| 场景 | 期望 |
| --- | --- |
| 说“做一张保护同伴的卡” | 自动确定已有能力是否足够，保存真实草稿，不只回复文字 |
| 选中 A 后发消息，发送后切到 B | 执行仍作用于发送时的 A；界面能说明对象 |
| 人工改生命后旧 AI 回执到达 | 保留人工值，旧结果只进入历史 |
| 只改数值 | 不调用生图，重新校验相关行为与展示 |
| 从青玉换到宣纸 | 美术和规则复用，界面与游戏主题一致 |
| 已打开试玩，后台产生新版本 | 当前局不变；明确提示可切换 |
| 同时开两个候选、重用端口 | 内容、纹理和存档不串版本 |
| 生图提交超时但提供方实际已受理 | 查单/恢复，不重复提交付费任务 |
| 在组装或采用时关闭宿主 | 重开后恢复到明确状态，不出现半包成功 |
| 自动修复连续失败 | 达到限额后停止，保留成果与具体选择 |
| 候选制作期间外部修改正式卡牌 | 采用时发现冲突，旧确认失效，保留外部改动 |
| 同时制作两项都修改同一个奖励池 | 依赖/冲突可见，正式应用串行，不能互相覆盖 |
| 连点加入游戏 | 同一版本只应用一次 |
| 加入后再改其他卡，再撤销本次加入 | 不删除后来的无关改动 |
| 新 NPC 已登记但没放进地点 | 检查报告不可达，不能标为完整可玩 |
| 口才 5、6、7 分别遇到门槛 6 的同一选项 | 低于、等于、高于的可用性和实际执行一致；无效属性有诊断 |
| 主角不知道秘密，或只在另一条路线知道 | 相关选项不提前泄露，其他人物也不会自动知情 |
| 第一章改变人物关系，第三章从不同入口再遇见 | 读取同一存档的共享事实，局部阅读位置和互斥路线保持正确 |
| 插入对白、重排选项、移动场景文件后继续旧档 | 稳定身份不变；不兼容变化提供明确迁移，不能回到错误对白 |
| 修改长篇中的一个场景或某人物的全部对白 | 范围和影响可定位，局部编译/重检，不覆盖无关内容或人工锁定项 |
| 一章上千条对白、全书 30 万字 | 按固定压力样例实际测量加载、搜索、修改、运行与存档；不以能保存大文件判定通过 |
| 地图没有有效出口、奖励可重复领取 | 行为检查失败并定位，自动修复或明确阻塞 |
| 新机制只有 enum/文案，没有处理器 | 能力检查失败，不以类型检查通过冒充支持 |
| 工作流、执行台和试玩便笺显示完成 | 三者引用同一候选及事实，不从各自旧 state 推测 |
| 在卡牌库、世界、知识库、生产或试玩查看内容 | 没有独立加入/撤销或固定“查看功能进展”底栏；交付在功能进展按同一 ID 完成 |
| 在功能进展确认一个跨领域功能 | 同一候选的卡牌、NPC、地图、代码及依赖整包采用；其他功能的候选保持原样 |
| 已加入的功能产生新候选 | 保留原采用记录，新候选重新验收和确认，不能显示为已经加入 |
| 点击任意便笺自带的会话按钮 | 打开 DSH 原有消息面板和相应会话，携带发送时选中对象；内容区域没有第二个讨论入口、输入框或消息历史 |
| 工作流产生新候选 | 自动登记到试玩便笺，保留版本与目标；其他便笺不新增试玩按钮、不强制跳转 |
| 查看人物、剧情或功能进展 | 保留本职内容与必要操作；流程状态和引导文案不在多个位置重复 |
| 在现有功能进展接入游戏工作流 | 原功能列表、搜索/筛选、折叠、归档、决策记录与 PR/CI/部署仍可用；只对相关功能项补充候选与采用能力 |
| 创建一件消耗品/装备/任务工具 | 自动补齐获得、图标、使用/持有条件、反馈与存档；满生命不吞药、卸装不保留修正、银针检查不消耗工具 |
| 从道具/人物/场景进入素材并返回 | 保留同一对象身份和版本，定位正确引用；类别不同不复制定义 |
| 只改一条对白或一项数值 | 精确失效关联配音/字幕等衍生；不无故重生全部美术 |
| 进入、离开和反复进入场景 | 背景/层/音景引用正确；音乐不叠播，动效和音频释放；静音仍有视觉反馈 |
| 文本变长、切换语言或窄屏 | UI 重排且焦点可达；字体无缺字；文字不依赖静态背景中的字 |
| 必需素材缺失而可选配音未做 | 必需缺项阻止完整采用；可选项不误阻断；占位试玩和真实完成明确区分 |
| 采用可选 3D 生产路线 | 源件、材质/骨骼、配方和渲染输出分别可追溯；渲染图不冒充可运行模型 |
| 全新机器启动发布包 | 可正常玩，无作者机器资源、临时 URL 和创作密钥依赖 |
| 不会编程的目标用户完成一次创作 | 全程原生对话和直接预览，无技术文件操作 |

实施时只运行受影响的最小测试集合。纯布局用真实 UI 核验，不写镜像测试；并发、版本、采用、生命周期和存档行为需要回归测试。发布候选执行预先定义的关键旅程，不因通过构建就标所有行为完成。全量测试另按项目约定获得明确授权。

## 14. 首要风险与设计取舍

| 风险 | 处理方式 |
| --- | --- |
| 生图能力无法自动接入 | M0 先验证；真实能力状态可见；开发期保留协作交接，但不把它算新手正式完成 |
| 多个写入口绕过最终确认 | 从工作区与工具能力限制开始，统一 mutation 范围，不能只藏按钮 |
| 新机制随意生成导致不可测试 | 先登记实际能力；新增源码配方绑定示例、反例和状态契约 |
| 美术好看但不适配游戏 | 使用最终布局与实际游戏尺寸验收；先固定风格与构图再扩量 |
| 方案规模过大，长期没有可玩结果 | 每阶段交付完整可玩的变化，先单卡，再一段冒险，再整游戏 |
| 长篇人物/分支组合失控，简单界面掩盖底层缺口 | 先统一人物与条件语义，采用章节/片段、分支汇合和共享事实；真实章节与规模压力分别验收 |
| 数据“统一”变成重写所有老系统 | 先加适配和校验，再处理出现的重复，不先建设抽象平台 |
| 自动化费用或返修失控 | 有界重试、预算、缓存复用；显示真实消耗和未知项 |
| 发布承诺超过实际能力 | 区分已实现、已验收、规划；新手完成率与独立发布包分别验收 |

近期不建设通用节点编辑器、模型超市、任意游戏类型引擎、多端协作平台或完整 3D 动画工具链。所需能力有实测需求时，以配方/适配器增加。
