# 人物、任务与长篇剧情：保持简单操作，支持复杂叙事

2026-09-26 · 对[游戏创作桌面总规划](cardgame-creation-studio-plan.md)的补充与修订。状态：**规划，尚未实现和验收**。

## 1. 结论与本次要求

前一版“狐爷爷发委托”的草案仅展示创作流程，没有完整设计人物和剧情系统。现有代码具备一些基础，但不能据此承诺已经能制作、维护和运行十几万字的复杂剧情。此次把人物与长篇叙事列为核心能力，并在首个正式创作版本之前验收。

本次要求与验收范围：

- 主角与 NPC 都有可扩展的人物模型，口才等点数、身份、关系、已知信息和经历能真实影响选项、事件及后续剧情。
- 支持十几万字以上的作品、一章几百到上千条对白，能定位、局部修改、编译、试玩和保存；不能只做到存下大文本。
- 默认界面和流程保持简单，复杂规则主要通过 DSH 原生消息面板编辑；不新造对话面板，不要求填写几十个字段或连接成千上万个节点。
- 对话只用便笺自带按钮，试玩只在已有试玩便笺操作；人物、剧情、任务和功能进展均不再增加同义快捷按钮、讨论栏或固定跳转底栏。完整数据模型不意味着把全部能力同时铺在界面上。
- 地图、卡牌、人物、剧情和任务使用同一游戏事实；所有最终采用、记录和撤销仍统一在现有功能进展。
- 保留现有游戏和便笺身份、已有剧情、属性尺度及存档；允许改造游戏本体，迁移必须明确。

## 2. 当前实际基础与缺口

本次核对的是已连接到游戏场景的路径，不把设计文档或类型声明等同于已具备运行能力。

| 已核对事实 | 可以复用 | 必须补齐 |
| --- | --- | --- |
| `types/story.ts` 和 `state/StoryState.ts` 已有数值比较、旗标、访问记录、对话记录，以及 all/any/not | 现有确定性条件求值和状态变更 | 属性定义、人物对象、关系/任务/道具/知识条件；未知属性诊断，目前缺失数值会按 0 参与比较 |
| `storyFlowViewModel.ts` 已分别处理 `visibleWhen`、`enabledWhen` | 隐藏与禁用选项的现有语义 | 作者能看到具体条件及原因，文本、任务和事件使用同一求值结果 |
| 运行状态已有 `attributes`、`relations`，主角 seed 有悟性 60、心性 55、机缘 50 | 已有主角属性和关系变化 | 主角/NPC 的统一身份、技能成长、关系方向、知识和状态；不能把现有 0–100 属性直接改成 0–10 |
| 当前 `world/npcs.json` 的样例主要是姓名、性别、境界、阵营、角色、标签和描述 | 人物 ID 与基础设定 | 能参与剧情判定的能力、目标、关系和运行状态；人设文字不能替代这些事实 |
| 当前六份剧情 JSON 样例各为 2–9 个节点，其中主线 `story-graph.json` 为 7 个节点、6 个选项 | 短剧情、分支及战斗往返 | 尚无千条对白、跨章人物或长篇容量证明；节点数与对白条数不能混为一谈 |
| `StoryScene` 按资源加载整张剧情图；视图构建时建立节点索引并过滤全图选项 | catalog 资源身份、加载与校验入口 | 按章节/场景加载、复用索引、分块阅读和增量编译；此处是待测风险，不宣称现状已经卡顿 |
| Worka `compileStory` 当前把 Markdown 场景链接编译成选项，生成的 `onEnter`、`effects` 为空，未编译选项条件 | 文档索引、链接诊断、编译登记 | 从写作源到游戏真实条件、后果和对白条目的完整链路 |
| 当前编译节点 ID 来自文档路径，选项 ID 带顺序号 | 既有内容的读取能力 | 稳定 ID 与旧 ID 映射，移动文档或插入选项不能改变存档含义 |
| `StoryHubSessionPersistence` 按 Hub、action、图文件保存各自进度；`GameWorldState` 已聚合剧情、仓库、秘境存档视图 | 存档边界、兼容登记、只读聚合及现有仓库写入能力 | 跨章节共享人物、关系和世界事实的明确权威写入边界；聚合视图本身不等于已有统一叙事状态 |
| 同时存在可玩 StoryState 契约与 `storyContent.ts` 的另一套 executable 契约 | 保留已登记资源兼容 | 收敛到一套运行语义，通过适配处理旧格式，不能再增加第三套独立判定 |

因此下一步不是给人物便笺多加几个输入框，而是打通“人物定义 → 本局状态 → 条件/结果 → 章节内容 → 试玩验证”。

## 3. 人物模型：一套基础，按角色补充

### 3.1 先分清人物设定与本局状态

同一个人物保持稳定身份。创作者定义他是谁、初始能力和剧情用途；存档记录这一局他发生了什么。修改人物设定不会无条件覆盖玩家已积累的关系和经历。

| 层次 | 典型内容 | 如何影响游戏 |
| --- | --- | --- |
| 身份与表现 | 名称、外观、年龄阶段、出身、阵营、职业、称谓、声音/立绘引用 | 身份限定选项、称呼和表现；年龄阶段等纯资料只有明确绑定规则后才参与判定 |
| 能力 | 已有悟性/心性/机缘；按项目添加口才、洞察、医术、潜行等技能 | 固定门槛、技能成长、可选的对抗或随机检定 |
| 特质与经历 | 守信、怕火、救过某人、欠某人情、背叛过门派 | 特殊台词、事件资格和人物反应；自由描述不自动变成生效规则 |
| 人物目标与弧线 | 想保护什么、害怕失去什么、说话方式、不能违背的设定、预期转变 | 指导 AI 写作与一致性审核；预定未来不当作本局已发生事实 |
| 关系 | 甲对乙的信任、好感、敌意；角色与阵营的声望 | 决定求助、交易、告密、入队与分支；方向明确，不能假设双方数值相同 |
| 知识与秘密 | 某人知道、怀疑或相信什么，以及获知来源 | 防止主角没听过的秘密出现在选项中，或所有 NPC 同时获得同一知识 |
| 当前状态 | 所在地点、生死、伤病、情绪、可交谈状态、临时效果 | 事件是否能触发、对白变体与交互；只实现实际剧情需要的状态 |
| 持有与参与 | 道具、货币、卡组/战斗配置引用、所属队伍、关联任务 | 消耗与奖励、身份验证、战斗或任务入口 |

这是一组可组合能力，不是要求每个 NPC 都填完整表格。路人可以只有身份和两句对白；重要人物再拥有目标、关系、技能和个人剧情。无用字段不展示，不自动生成无用途的几十种属性。

### 3.2 主角使用同一人物基础，增加玩家成长与选择

主角补充：可选出身、玩家决定的性格/身份标签、成长点与技能分配、装备/临时修正、队伍、任务日志、关键选择、已知线索、可用卡牌及资源引用。默认使用母版提供的成长规则，用户不必自己设计全部公式。

每种点数都登记稳定 ID、名称、单位/范围、默认值、来源、成长规则、可见性和存档策略。能力最终值只计算一次，由剧情、人物页和试玩检查共用；可以显示“口才 6 = 基础 5 + 师承 1”。装备、受伤和临时效果不重复加算，取消效果后可解释地恢复。

原有悟性等点数保持现有尺度。示例新增技能使用 0–10，关系使用 0–100，只是本方案样例，不是全项目被强制换算。属性改名只改显示名；删属性、改尺度或成长规则需要影响清单及存档迁移。未知字段不能静默当成零来决定剧情。

主角、当前对话者、指定 NPC、队友分别绑定明确对象。不会因为对话对象变化而把“主角口才”误读为“NPC 口才”。NPC 自己的能力也可以影响剧情，例如医术不足时无法救治，洞察较高时识破伪装。

新增普通数值属性、身份或关系维度通常属于数据创作；新增尚不存在的计算公式、时间机制或行为效果仍走总规划中的机制开发与验证。不能因为能存一个字段，就声称与它有关的全部玩法已经可用。

### 3.3 对用户只展示当前有用的部分

人物详情默认显示：人物摘要、关键能力、主要关系、相关剧情。选中某一能力可查看“哪些场景会读它”；选中关系可查看来源与变化。其余字段按需展开。

可以直接说：“这个掌柜很精明，口才一般骗不过他，但救过他妹妹的人可以赊账。”AI 补成明确规则，并用白话回显差异。只有“赊账是否会影响主线”这类关键歧义需要确认；不逐项询问所有默认字段。

## 4. 一套条件与结果，支撑选项、事件和任务

### 4.1 区分四个问题

| 问题 | 示例 | 默认处理 |
| --- | --- | --- |
| 事情能否发生 | 狐爷爷还活着、玩家到药铺、当前是第二章、委托未结束 | 事件/场景的进入条件；不满足则不触发 |
| 玩家能否看到这个选择 | 主角是否已经知道药方被盗 | 未知秘密默认隐藏，避免泄露剧情 |
| 看到了能否选择 | 口才是否达到 6 | 默认显示锁定及“需要口才 6，当前 4”；作者可决定是否展示具体门槛 |
| 选择后发生什么 | 信任 +10、花费药草、记住承诺、进入不同对白 | 结构化结果与叙事文本一同生成和验收 |

可复用的条件只覆盖实际需要的类型：数值比较、身份/特质、人物关系、道具/货币、人物知识、任务阶段、世界事实、地点/时段、曾经的选择或访问，以及 all/any/not。条件编辑默认显示自然语言；专家才展开结构详情。

**首版默认确定性门槛。** 例如口才 ≥ 6 时可说服，结果清晰可测。只有用户明确要求冒险或不确定性时，才启用已登记的随机/对抗检定。检定规则由项目定义，使用可重放随机源，保存结果与尝试记录；显示选项、刷新界面或读取存档不能偷偷重掷。是否允许提升能力后重试是显式规则。

### 4.2 条件、扣除和后果作为一次游戏动作处理

展示选项与真正选择时都核对状态。物品不足、NPC 已离开或条件发生变化时，返回可理解的反馈。成功动作把消耗、关系变化、任务步骤、知识和下一位置一起提交，并保存可恢复的结果；不能出现药草扣了、剧情没前进的半完成状态。

“只触发一次”要声明范围：这一局、这个任务实例、这一章或每次交谈。按范围和稳定事件 ID 记录，不靠一句对白猜测已经发过奖励。重新打开对话、战斗返回、读档和双击均不重复结算。

### 4.3 事件只在相关变化时检查

先支持进入地点、开始交谈、推进明确的游戏时段、完成任务步骤、获得知识、关系跨过门槛等触发点。按事件和读取字段建立索引，只检查受影响事件；不在每帧扫描所有人物和剧情。

章节、天数和时段使用明确的运行值，日历文案只是展示。需要限时任务时明确从何时起算、哪些行动推进时间、超时后的路线，不用“第二天晚上”这类未结构化文字直接作运行判定。

同一时刻有多个事件时，使用明确优先级、互斥组和固定顺序。一次动作的连锁触发有步数上限，检测循环，失败保留诊断；不允许一个事件无限激活自身。默认不做所有 NPC 全天候自主模拟，也不让真实时钟悄悄跳过重要剧情。

### 4.4 游戏任务与创作待办分开

Worka 待办记录“作者想做什么”；游戏任务记录“玩家这局在做什么”。两者引用关联，但身份、进度和完成条件各自明确。

任务具有阶段、目标、参与人物、进入/失败条件和奖励；常用状态为未解锁、可接、进行中、完成、失败。任务可有并行目标、可选目标、互斥路线与跨章后果。默认从简单模板扩展，不要求先配置任务树。

例如“救狐爷爷”允许采药、请医师、交换药方三条完成方式，统一推进到同一个关键事实，同时留下不同的人情和资源后果。任务日志只向玩家展示他当前知道的目标；失败也有后续反应，不能一律变成剧情死路。

## 5. 用“雾林遇狐”检验复杂度，而不只演示发奖励

下面数值是待制作样例，不代表已经写入游戏。

初始测试主角：口才 4、洞察 5、医术 2；狐爷爷对主角信任 20。另备“口才 6”的测试主角。狐爷爷是隐瞒身份的医师，有保住旧药方的目标；人物设定中的秘密与主角是否知道秘密分别保存。

| 内容 | 条件 | 玩家看到与发生的变化 |
| --- | --- | --- |
| 药铺初见 | 第二章、白天、狐爷爷在场且存活 | 进入初见；记录见过人物，重复拜访进入不同开场 |
| “我会替你保守秘密” | 主角知道药方被盗；口才 ≥ 6 | 不知道时隐藏；知道但口才 4 时锁定；达到门槛才可选择，成功后信任 +10，记录承诺 |
| “你的手一直在发抖” | 洞察 ≥ 5 | 解锁观察对白，主角获知他中了毒；不使其他 NPC 自动知情 |
| “我可以当场施针” | 主角已知中毒；医术 ≥ 4；有银针且未受严重手伤 | 扣除规定耗材并推进治疗阶段；不足时说明实际缺项 |
| 普通帮助路线 | 狐爷爷还活着且任务未结束 | 口才和医术低也能采药完成主要目标；保留不同代价与对白 |
| 向守卫告密 | 主角已知身份且守卫可交互 | 守卫获得该知识；关系改变；以后狐爷爷回应此事，不能继续使用“从未见过你”的开场 |
| 委托完成 | 任一合法救治路线达成 | 统一完成任务，首次发灵狐卡；各路线的人情和承诺分别保留 |
| 第三章求助 | 人物存活、信任 ≥ 30、存在守密承诺且未告密 | 开启额外帮助；低信任或告密有替代反应，不偷改为相同结局 |

测试预设应命名为“普通来客”“善于交涉”“懂医术”“曾经告密”，一键从对应场景开始。作者能看到每个选项的依据与状态差异，实际发布的玩家界面只显示设计允许公开的信息。

这一个样例应贯穿人物、属性、知识、关系、道具、任务、卡牌奖励、跨章记忆和存档，不必先制作几十条彼此重复的支线。

## 6. 长篇剧情：按书组织，按局部编译和运行

### 6.1 内容层级与默认阅读方式

使用“作品 → 章节 → 场景 → 对话片段/选择”，对白行属于片段。一章 1,000 条对白不等于 1,000 个分支节点；连续交谈可以是一个包含多行对白的片段，仅在真实选择、事件和可复用片段处形成结构。

每条对白/旁白有稳定 ID、说话者引用、文本及可选情绪/表现提示。说话者名字变化时不需要手工替换整部作品。ID 同样给存档位置、内容定位以及后续配音/本地化保留基础，首版不强制制作配音。

正文默认按剧本阅读。章节与人物入口先用知识库已有 Markdown 索引页、普通链接和反向引用组织；现有文档与链接无法完成定位时，再补通用文档搜索或索引能力。条件和分支按需查看，绝不默认渲染全书所有台词节点。

长场景对白分块加载与渲染，保留原文行号和定位；其他文档继续走普通 Markdown 阅读。若实测通用搜索或人物引用返回过大，再按需分页。compact 便笺保持已有摘要，expanded/聚焦视图读正文；不靠缩小字体把整章塞进便笺。

### 6.2 控制分支数量，保留选择的后果

优先使用局部分支、重新汇合、条件对白和可复用对话片段。汇合后保留关系、知识、物品与承诺等状态，后文仍能回应过去选择；只有真正改变大方向的决定才开启长期路线。

每章记录自己的目标、进入条件、人物变化、关键决定和对后文的承诺。可重复交谈、一次性片段、呼叫并返回的子场景以及退出都需明确语义。循环必须有玩家可用的退出或设计上明确的终点，不把所有循环机械判为错误。

### 6.3 写作源、运行包与索引职责明确

保留文件优先：以场景为常用写作文件单位，在现有 Markdown 创作源上增加受约束的角色、对白 ID、条件和结果结构；不要求作者手写这些结构。具体语法通过样例验证后确定，首版不另造一门通用编程语言。

- 写作源：正文与同一场景的结构规则一起维护；角色设定和属性定义使用关联的稳定引用。
- 编译产物：由同一编译器生成章节/场景包、对白与出边索引、引用清单、版本及源码定位映射。运行包只由编译产生，不成为第二份人工编辑源。
- 查询索引：人物出场、属性读取、旗标读写、任务引用、全文搜索与诊断均可重建；复用现有 content 服务的数据库和索引机制，不另建一套私有知识库。

通过显式 ID 和迁移映射替换“路径/顺序号即身份”的旧方案。插入第一项选项、移动场景文件、重排章节都不能让旧存档指向另一句话。

游戏只加载当前场景所需的章节/片段及依赖，必要时预取下一段；节点与出边索引在内容版本加载时建立并复用。修改一段对白只重编受影响场景；修改公共属性、复用片段或跨章事实则沿引用关系重新检查所有受影响位置。首次全量校验和发布校验仍覆盖整个叙事内容包。

### 6.4 AI 不能靠一次读完整本书维持一致性

写作时提供有版本的相关上下文：已确认的世界设定、当前章目标、相关人物档案、必要前后文、条件依赖、未收束的伏笔和人工锁定项。摘要只用于检索与导航；引用到的关键事实需要读回原文及规则，不把摘要当事实权威。

人物目标、伏笔和时间线均标注来源和适用路线。“玩家在 A 路线已经杀了某人”不能被摘要合并成所有路线的既定事实。计划中的结局也不能提前作为主角已知信息。

默认分章规划、分场景生成和修订。比如“把第三章掌柜所有对白改得圆滑一点”先定位此人全部出现位置，再做带版本的局部修改，保留无关正文、条件和人工锁定内容。批量修改给出影响范围、进度与可恢复的批次；不因模型上下文不足而截断整章后覆盖原稿。

十几万字需要经过多批次生成和审校；不承诺一句话一次生成即达到成品质量。用户仍可先只提供 idea，系统默认完成一个可试玩场景，再按同一方向逐步扩展。

## 7. 跨章节状态与存档

扩展现有 `GameWorldState` 聚合和存档 owner 边界，增加最小必要的共享叙事权威状态与命令；不在每张图里复制一份主角，也不把原存档系统整体替换掉。

| 作用域 | 保存什么 | 不应混入什么 |
| --- | --- | --- |
| 游戏内容定义 | 人物原型、属性目录、任务/场景定义、默认值和规则版本 | 某玩家本局的结果 |
| 当前存档的共享事实 | 人物实例、成长、关系、知识、任务阶段、跨章选择、世界时段 | 作者的生成进度与未来剧情提纲 |
| 场景/对话会话 | 当前片段、对白位置、局部变量、返回栈、临时选择 | 重复保存可独立变化的主角能力与全局关系 |
| 预览检查点 | 对应内容版本的测试人物、世界快照、种子和入口 | 正式玩家的存档 |

多个 Hub 入口引用同一人物和世界事实，但各自的阅读位置、独立剧情实例可按设计分别恢复。秘境带回道具、剧情消耗道具和卡牌奖励沿用已有资源/仓库权威服务。内容中的 effect 是命令，不直接绕过服务修改另一块存档。

已有多份局部存档迁移为共享状态时，需要登记字段归属与冲突策略；不能简单合并字典或“取最大好感”，否则会把互斥路线混成同一局。无法无损判断的旧进度保留旧版本兼容路径，或明确只让新开局使用新规则，不静默重置。

保存时包括内容版本、场景/对白位置、必要的返回栈与事件结算记录。纯文字修改可以兼容；删除当前对白、改变分支目标或任务状态结构需要映射到明确的续接点和迁移校验。修改已开始游玩的章节不在后台强制替换当前会话。

## 8. 简单的 Worka 操作，不增加一套创作后台

人物、任务、剧情继续用同一知识库的文档和链接组织，保持原便笺和会话。文档标题可区分“人物”“剧情”“游戏任务”与 Worka 创作待办；新增展示入口以前先验证现有文档、链接、搜索和引用是否真的不足，不为每个人物/章节增加便笺。

| 当前在做什么 | 默认看到什么 | 常用轻量操作 |
| --- | --- | --- |
| 看人物 | 简介、关键能力、关系、最近相关剧情 | 选中字段、简单编辑、按需查看引用 |
| 写剧情 | Markdown 章节索引页、当前场景正文或分页对白 | 沿链接跳转、查看引用、修改正文 |
| 看游戏任务 | 玩家目标、当前阶段、关联人物及不同完成办法 | 查看触发原因、跳转相关场景 |
| 查某个分支 | 选中选项的条件、结果和后文影响 | 按需展开判定依据 |
| 试玩 | 现有试玩便笺中的候选运行画面 | 使用已有运行控件；测试主角和检查点在这里选择 |
| 准备交付 | 功能进展中的具体候选、影响章节/人物/存档和验收结果 | 统一确认加入、记录与撤销 |

所有“修改这里”的对话通过便笺自带按钮进入 DSH 现有消息面板，不在上述各视图内增加讨论按钮。原生消息链路绑定 `featureId`、人物/章节/场景/对白/选择引用、当前版本与选中范围；试玩反馈还附当前人物状态、已知事实和判断证据。不依赖长会话里记住了整本小说，不复制上下文展示栏。

作者在试玩便笺中选择普通主角和目标场景，也可以通过原生对话表达“用普通主角从这里开始”或“看看为什么这个选项没出现”；这些能力不再各自变成人物/剧情页的常驻按钮。测试状态变化仅作用于候选试玩；不会修改主角正式初始值或玩家正式存档。复杂条件先用自然语言编辑，提供按需核对的结构和差异，不做必须填写的规则表单。

改一个数值、修一句台词、排序和搜索仍保留直接操作；跨人物、跨场景的复杂修改由 DSH 对话承接。简单不能变成每改一个字都必须等 AI，复杂也不能变成必须学习一套节点编程工具。

## 9. 容量与正确性必须有独立验收

### 9.1 第一档长篇容量目标

以下是**拟定验收目标，尚未实测，不是现有能力承诺**：

| 维度 | 首档目标 |
| --- | --- |
| 全书正文 | 至少 30 万中文字符，统计对白/旁白有效正文，排除 ID、重复摘要和结构字段 |
| 章节与对白 | 20 章，合计至少 20,000 条对白/旁白；典型每章 500–1,500 条，至少一章达到 1,500 条 |
| 人物 | 200 个稳定人物，其中至少 50 个具有能力、关系或跨章事件用途 |
| 任务与选择 | 50 个游戏任务、至少 3,000 个选项；包含可合流、互斥、重复交谈和跨章延迟后果 |
| 状态 | 至少 5,000 个已声明的事实/知识/任务状态键，包含读取与写入索引 |

这是工程压力数据集，可主要自动生成，但必须使用合法、多样的条件和跨文件依赖，不能仅复制同一句对白。它证明容量与机制边界；文学质量另用一章真实编写、人工审阅的内容验收。结构合法但不可能到达的场景不能计作可玩覆盖。

固定普通笔记本级验收设备、系统、浏览器、构建版本和本地资产条件，记录冷启动/热缓存、至少 30 次操作的 p95 与最慢值。初始目标：章节首屏 1 秒内，已加载对白推进及选项判断 100 毫秒内，索引搜索 300 毫秒内，局部文本修改的增量编译与诊断 2 秒内。全库编译单独报告时长、内存和可见进度；不能把网络生成时间混进本地交互测试，也不能把它排除后宣称 idea 到完成只需 1 秒。

除耗时外，验证切换章节后的内存不随已读章节无限增长、已加载场景不扫描全部对白、编辑视图不挂载全书全部 DOM。以上目标在实现批次开始前固定测试方法，失败先定位瓶颈，不临时删掉压力样例来过关。

### 9.2 分层检查，避免承诺穷举所有路线

- 结构检查：ID 唯一、引用存在、条件类型/属性范围正确、场景出口、说话人及资源有效、旧位置映射完整。
- 行为检查：每个新增门槛覆盖低于/等于/高于阈值；复合条件覆盖决定结果的分量变化；关键选项的可见、可选、效果与文案一致。
- 路线检查：主线及设计支持的主要路线可完成；低属性仍有明确可行路径或设计允许的失败结局；秘密不提前泄露；互斥路线不会串事实。
- 状态检查：生死、关系、知识、任务、资源和存档前后一致；双击、重访、战斗返回与读档不重复给奖励；消费失败不提交其他后果。
- 长篇编辑检查：跨章影响可定位；批量改人名/语气不改变稳定 ID；插入选项不改变旧选择含义；人工锁定内容与并发修改保留。
- 叙事审查：人物说话是否一致、动机和伏笔是否合理，由 AI 辅助指出来源，再以真实阅读和试玩确认；不能把自动检查通过等同于故事精彩。

一般状态空间不能穷举。使用作者指定的关键路线、边界场景、组合抽样和有界探索；报告覆盖过的分支/条件及未覆盖范围。静态“图上连得到”与满足实际条件后可达分别报告，无法证明的复杂路线标待验，不虚报已验证。

## 10. 实施顺序与技术选择

总规划的 M0/M1 候选隔离、DSH 对话与功能进展交付仍先完成。人物和长篇基础从 M2 开始，不拖到发布后才补。

| 批次 | 完整交付 | 完成条件 |
| --- | --- | --- |
| N0：契约收敛 | 明确现有两种剧情格式的读取适配、人物/属性 ID、共享状态归属和源码位置映射 | 当前短剧情不丢语义；迁移边界和最小示例可执行 |
| N1：复杂的小场景 | 按第 5 节完成一个人物、主角能力、关系/知识/物品条件和游戏任务；DSH 编辑到可玩候选 | 高低属性、隐藏/禁用选项、重复奖励、修改后复测全部走通 |
| N2：一章的创作体验 | 500–1,000 条真实对白，分场景读写、人物出场索引、局部改写与测试预设 | 不需要作者打开技术文件或维护巨型图；不会改丢正文和规则 |
| N3：跨章与长篇压力 | 跨章事实、多个入口共享人物、章节包、稳定 ID、增量编译、存档迁移及第 9 节压力样例 | 容量与性能有实测记录，关键跨章路线和存档恢复通过 |
| N4：进入游戏与发布 | 功能进展整包采用、候选/正式隔离、影响清单、旧版本兼容和发布包实测 | 所确认的剧情、人物和规则版本一起生效；长篇运行不依赖创作时 AI |

N1 对应 M2 的复杂冒险闭环，N2/N3 是 M2 的长篇验收门槛；N4 沿用 M1 的采用机制并进入 M5 发布验收。可以先展示 N1，但在 N3 通过之前不宣称已支持长篇创作。

默认扩展现有 Phaser + StoryState + 内容编译服务，先解决现有两套契约不一致和写作规则未编译的问题。只引入所需的有限条件、效果、复用片段与调用/返回语义，不同时运行两套判定器。AI 在创作期生成内容，发布游戏按已编译规则运行；普通对白、条件和任务不需要实时模型推断。

参考 Ink 将文本分为可组织的片段、用变量表达后果和让分支重新汇合的做法；这些能力见 [Ink 官方写作指南](https://github.com/inkle/ink/blob/master/Documentation/WritingWithInk.md)。参考 Yarn Spinner 对条件对白、选项可用性与无可用选项时的后续处理划分，见 [Yarn Spinner 官方 Flow Control 文档](https://docs.yarnspinner.dev/write-yarn-scripts/scripting-fundamentals/flow-control)。这两项是结构参考，不代表本次安装了引擎，也不证明它们或当前代码已经通过本项目的长篇指标。

如果 N1/N2 表明维护常用写作结构已迫使当前编译器变成完整脚本语言，再单独验证成熟叙事引擎的适配、运行时依赖、存档和迁移成本；在同一压力样例上比较后做一次选型。不要现在同时支持自定义、Ink、Yarn 三种写法，把复杂度转嫁给作者。

## 11. 本次交付与验证边界

本次已核对相关源码、当前样例规模、初始主角数据、存档边界、现有 Markdown 编译行为，以及两份官方叙事工具文档；产出本规划并同步总规划中的优先级和验收项。

本次没有修改游戏运行时、便笺界面或写作格式，没有生成压力测试剧情，也没有执行容量/性能、真实长篇创作或新手测试。此前交互草案中的简短 NPC 页面仍只是流程示意，不能用作本规划已实现的证明。
